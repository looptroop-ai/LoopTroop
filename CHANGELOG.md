# Changelog

All notable changes and official releases for LoopTroop are documented here.
Unreleased changes appear first and represent commits that have not yet been included in a versioned release.

## Unreleased

> Changes merged since the last versioned release that have not yet shipped in a tagged version.

## 0.5.1 (2026-08-13)


### Summary
- Added a one-line install for macOS, Linux and Windows — `curl -fsSL https://www.looptroop.ovh/install | sh` and `irm https://www.looptroop.ovh/install.ps1 | iex` — which resolves the newest release that carries the files, checks what it downloaded against the checksum that release published, and refuses to install anything that does not match. It never installs Node and never asks for sudo.
- Made LoopTroop installable with Homebrew, Scoop and Chocolatey. This is the first release that publishes to all three, and it does so in parallel with npm and the container image, gating none of them, so a package channel that fails cannot hold up a release.
- Added a self-contained bundle to every release: the compiled application plus its dependencies resolved once, at build time. The three managed channels install that rather than resolving dependencies afresh on each machine, which is the difference between everyone running the versions the release was tested against and everyone running whatever their machine resolved that day.
- Fixed the upgrade command shown to anyone who installed with `npm install -g` on a machine whose Node came from Homebrew, which advised a `brew upgrade` that could only fail — and made the correction reach the people already holding the wrong answer.

### Fixed
- Fixed the upgrade command shown to anyone who installed LoopTroop with `npm install -g` on a machine whose Node came from Homebrew. Homebrew's Node puts global packages under the Homebrew prefix, which LoopTroop read as a Homebrew installation, so it advised `brew upgrade looptroop` — a command that fails, because no such formula was ever installed. Detection now looks for the Cellar entry Homebrew actually creates.
- Made that fix reach the people it is for. The install channel is detected once and then remembered, and reinstalling puts the files back where they already were, so the remembered wrong answer would have outlived any correction to detection. A remembered answer that contradicts the location it was recorded for is now treated as stale and worked out again.
- Stopped a configuration file naming a channel like `constructor` from being accepted as a real one.

### Added
- An installer may now state the channel outright by leaving a `.install-channel` file at the package root, instead of LoopTroop having to infer it from the install path. The three managed package channels all unpack the same files, so the path is often the only difference between them and sometimes not even that.
- A one-line install for macOS, Linux and Windows: `curl -fsSL https://www.looptroop.ovh/install | sh` and `irm https://www.looptroop.ovh/install.ps1 | iex`. It resolves the newest release that actually carries the files, checks what it downloaded against the checksum that release published, and refuses to install anything that does not match. It never installs Node, never asks for sudo, and installs through npm, so `npm install -g looptroop@latest` and `npm uninstall -g looptroop` keep working. The minimum Node and npm versions it enforces travel with the release rather than being written into the script, so an installer downloaded months ago still applies the right floor.
- Releases now carry a self-contained bundle alongside the npm tarball: the compiled application plus its dependencies resolved once, at build time, into a tree that runs anywhere with Node. It exists for the Homebrew, Scoop and Chocolatey packages that follow, which unpack it instead of resolving dependencies afresh on each user's machine — the difference between everyone running the versions the release was tested against and everyone running whatever their machine resolved that day. The build refuses to produce one containing compiled code, platform-specific packages, or anything needing an install step, and CI requires two builds of the same commit to be byte-identical and runs the Linux-built bundle on macOS and Windows.
- Every file a release publishes is now recorded in `release-manifest.json` with its size and checksum, and each one is verified on Linux, macOS and Windows before anything is published. Manifests written by earlier releases still parse.
- Installation with Homebrew, Scoop and Chocolatey, starting with this release. The package descriptions for all three are generated from one place, so a release cannot publish a formula and a manifest that disagree about which files that version is. Each release publishes to all three in parallel with npm and the container image, gating none of them, so a package channel that fails cannot hold up a release — and a repair workflow finishes any one of them afterwards without re-running the release. Publishing to any of them refuses to overwrite a newer version, refuses to replace a published version with different files unless an operator explicitly asks for a repair, and does nothing at all when the right version is already there. The three managed channels install a bundle built once per release with every dependency resolved at build time, so everyone on them runs the exact versions the release was tested against; installing through npm resolves version ranges on your own machine, as npm is supposed to. Prereleases never reach these channels, because neither Homebrew nor Scoop has a concept of one, and publishing a prerelease would make it what everybody gets. The Chocolatey package carries the files inside it rather than fetching them, so installing needs nothing but the feed; its submissions wait for moderation, which nothing else waits for, so a separate dispatch installs the approved package from the feed and checks it reports itself correctly. CI installs LoopTroop through Homebrew on macOS and Linux and through Scoop on Windows — from a throwaway tap and bucket, never the public ones — checks the result runs and knows which command upgrades it, and packs, installs, runs and uninstalls the Chocolatey package to confirm nothing is left behind.

## 0.5.0 (2026-08-12)


### Summary
- Restructured the server into an embeddable runtime that performs no work when imported, so tooling can load it without starting a server, opening the database, or installing signal handlers.
- Added a production build that bundles the server and ships only compiled output, cutting a global installation from roughly three hundred packages to sixteen.
- Made the production server serve the interface itself, so a single command opens a working application on one address with no separate web server to configure.
- Moved the public website and published documentation into a dedicated repository, leaving the application checkout and development stack focused on LoopTroop itself.
- Repaired documentation and README media references after the website and documentation moved to their standalone repository, restoring the walkthrough GIF without duplicating the asset.
- Replaced the native `better-sqlite3` database driver with Node's built-in `node:sqlite`, removing the last compiled dependency from the runtime and eliminating the most common cause of failed installations.
- Introduced schema versioning for both the application and per-project databases, so a database written by a newer LoopTroop is refused with a clear message instead of being silently and destructively downgraded.
- Established the first CI workflow to enforce lint, typecheck, test, build, and clean-tree checks on every push and pull request. The required lanes all run the exact toolchain the package declares — Node 24.15.0 and npm 11.12.1 — on Linux, macOS and Windows, because the floor is a promise on all three. Non-blocking lanes track the newest Node 24 patch and Node 26 so upstream breakage arrives as news rather than as a failed required check.
- Downgraded `@types/node` from 26 to 24 to prevent accidental use of Node 26-only APIs while targeting Node 24 LTS as the minimum supported runtime.
- Declared the runtime Node floor (`engines.node`), pinned the package manager, and added `.nvmrc` so CI can enforce the minimum without testing only the latest patch.
- Fixed a latent development-server bug where `@codemirror/merge` would fail to load in the diff editor because Vite's dependency optimizer was configured with `noDiscovery: true` but the package was missing from the pre-declared list.
- Removed direct email and Twitter contact links from the web landing page footer.
- Pointed all in-app documentation links at the independently hosted documentation site and removed the local docs server from the app development stack.
- Made `npm run dev` verify-only, so starting the development environment no longer silently updates dependencies, rewrites the lockfile, or upgrades the OpenCode CLI; those updates are now explicit opt-in commands.
- Made `package.json` the single source of truth for the application version, enforced in CI, so the version shown in the app interface can no longer drift from the released version; the website independently reads the latest stable GitHub Release.
- Wired the root changelog to release notes: publishing a release now derives its notes from `CHANGELOG.md` instead of being written by hand, so the two can no longer disagree.
- Moved routine dependency updates onto a predictable weekly schedule with a maturity delay, so updates are reviewed in batches and security fixes still arrive quickly.
- Added governance documents (`SECURITY.md` and generated third-party notices) and wired the notices into CI, so a missing licence or stale notices file fails the build. The notices cover both the packages installed at runtime and the interface libraries compiled into the shipped bundle, which no dependency scan can see on its own.
- Added a `looptroop` command that runs LoopTroop as a background service: `setup`, `start`, `stop`, `restart`, `status`, `open`, `logs`, `doctor` and `clean`. `start` detaches from the terminal and keeps running after the shell closes, so the application is no longer tied to a terminal window left open.
- Limited each configuration directory to one running daemon, held by a lock that records which process took it rather than only when it last checked in. Two daemons sharing one set of databases and worktrees is the failure this prevents, and a suspended laptop no longer looks like an abandoned lock.
- Separated browser sessions from script access. A browser is signed in through a single-use code carried in the URL fragment, which is never sent in a request line and so cannot reach an access log, and exchanges it for a session cookie that scripts cannot read. Automation uses a separate bearer token. There is no way to authenticate by query string.
- Restricted accepted requests to this machine and to this daemon's own address, and made the session cookie usable only on requests the browser itself vouches for as same-origin. Another page served from a different port on the same loopback interface cannot drive this daemon with the cookie the browser would otherwise attach for it, since cookies carry no port scope of their own.
- Made the daemon manage the OpenCode server it depends on: it adopts one already running on the configured address or starts its own, records which of those happened, and stops only servers it started.
- Added a one-a-day update check that names the upgrade command for the way this copy was actually installed, and prints nothing when the check cannot reach the registry.
- Made the shipped package verifiable as a package: CI packs it, installs it globally on Linux, macOS and Windows, and drives a whole session from an empty directory — including one run from an installation the kernel makes read-only, which is what a global install on a shared machine is.
- Added a signed-out screen, so a tab whose 12-hour session has ended says so and names the command that signs in again, instead of rendering an interface whose every request is refused.
- Made releasing a version an automated, resumable operation rather than a sequence someone has to perform correctly by hand. A release is cut by merging a pull request that raises the version; the workflow then builds the package once and publishes those exact bytes to every channel. Because publishing is several irreversible steps in a row, the workflow first reads what already exists — the tag, the GitHub Release, the registry — and resolves a state from it, so a run interrupted halfway resumes from where it stopped instead of starting over or refusing to continue. Three situations deliberately stop it dead rather than being repaired: a tag that names a commit other than the one being released, a version already on npm under different bytes, and a version whose bytes are right but whose install tag points elsewhere. None can be corrected by retrying, and all three mean something happened outside the workflow. A run only calls a release finished once it has compared the bytes on the registry against the bytes it built; having every channel in place is not by itself proof, so a run that cannot make that comparison reports it as unverified rather than as done.
- Published the CLI to npm as `looptroop`, installable with `npm install -g looptroop`, with the package's authenticity established by npm's trusted publishing rather than by a long-lived token stored in the repository.
- Made raising the version refuse to proceed when the changelog entries it would publish are not publishable, using the same reader that renders the release notes rather than a looser check of its own, so a release cannot get as far as a pull request and then fail at the point of publishing.
- Made the container image a release channel rather than a Dockerfile nobody ran. It is now built on every push for both architectures, pinned to its base image by digest, labelled with the version and the commit it came from, and driven from inside a running container by a smoke test that proves the daemon starts as an unprivileged user, keeps its API closed without credentials, and shuts down cleanly when asked.

### Changed
- Applied the loopback-only network boundary to every bind address, including one supplied directly by an embedding host rather than through the environment. There is deliberately no host setting in `config.json`, so the control interface cannot be published to a network by editing a configuration file.
- Split the server into an embeddable runtime (`createRuntime`) and a thin daemon entry point. Constructing a runtime no longer creates directories, starts timers, binds sockets, or registers signal handlers; all of that now happens explicitly when the runtime is started, and signal handling belongs to the executable rather than the library.
- Made cross-origin request handling conditional on the build mode. Development keeps the allowances the Vite dev server needs across ports; production serves the interface and the API from a single origin and sends no cross-origin headers.
- Reclassified twenty-one interface-only packages as development dependencies now that the interface is bundled ahead of time. A production installation no longer downloads React, Radix UI, or CodeMirror.
- Moved the built interface to `dist/client/` and the bundled server to `dist/server/`, so the two build steps can no longer overwrite each other's output.
- Made the development preflight aware of a running background daemon, so starting the development stack can no longer mistake the daemon for a stale process tree and terminate it.
- Moved the canonical changelog back to root `CHANGELOG.md`, pointed contribution and release tooling at it, and changed all app documentation links to the independently hosted `looptroop-ai/LoopTroop-Website` site.
- Changed the public landing page version badge to read the latest stable GitHub Release in the visitor's browser with a six-hour cache and graceful offline fallback, avoiding any cross-repository release synchronization.
- Updated landing page hero headline typography scaling and wrapped phrases inline to prevent awkward per-sentence line breaks across viewports.
- Adjusted vertical padding between the Hero and Why LoopTroop sections in `web.html` to eliminate excessive empty space left after removing the tech logo wall.
- Updated the "Start here" links header in `README.md` to link to Ticket Lifecycle Screenshots instead of Ticket Flow.

### Added
- Added a settings file at `config.json` in the LoopTroop configuration directory, resolved with the precedence command-line flag, then environment variable, then file, then built-in default. Unrecognised keys are preserved when the file is rewritten, so settings written by a newer version survive being loaded by an older one, and a malformed file is ignored with a warning rather than preventing startup.
- Added a production server build that bundles the application's own source while leaving runtime dependencies to be installed normally, so the published package runs on a plain Node installation without a TypeScript loader.
- Added an explicit published-file allowlist covering the compiled output, licence, notices, readme and changelog. Without it the build output would have been excluded from the package, because it is deliberately untracked.
- Added a test that asserts the runtime performs no work when imported: no files written, no timers started, no signal handlers registered, and no socket bound until the runtime is explicitly started.
- Added static file serving to the production server, so the built interface is delivered by the same process that serves the API. Hashed build assets are served with long-lived immutable caching, while the entry document is always revalidated so a new version is picked up immediately instead of the browser reusing a stale page that points at deleted assets.
- Added a single-page-application fallback so deep links and browser reloads resolve to the interface instead of returning a not-found error. Unknown API paths, non-`GET` requests, and requests for missing build assets still return a genuine not-found response rather than being answered with the interface document, which would otherwise surface to the browser as a confusing script type error.
- Added an X / Twitter profile icon for `@liviusa` to the left of the main LoopTroop X icon in the landing page footer social icons block.
- Added `SECURITY.md` with a private vulnerability reporting route, a documented threat model that distinguishes intended local behaviour from genuine boundary escapes, and a statement that LoopTroop collects no telemetry and never reads provider API keys.
- Added generated third-party licence notices covering all 80 npm packages redistributed with the application: the 15 installed at runtime plus the 65 interface libraries compiled into the shipped bundle. The bundled set is recorded by the interface build itself rather than maintained by hand, so a new interface library cannot ship without its licence. Generating the notices requires a completed build and fails loudly without one, rather than quietly emitting a file that omits every bundled library. A CI gate fails when the file is out of date or a package declares no licence.
- Added a Renovate configuration for scheduled dependency updates, validated in CI: weekly grouped pull requests, a 7-day release-maturity delay, a 2-day window for security advisories, auto-merge limited to development dependencies, and per-package rules holding `drizzle-orm`/`drizzle-kit` on the release-candidate tag, delaying `@opencode-ai/sdk` by 30 days, and keeping `@types/node` on the supported major. Credentials and scheduling are enabled separately.
- Added a release-notes extractor that parses root `CHANGELOG.md` and emits the GitHub Release body for a given version, preferring `Release Highlights` and falling back to `Summary`. It fails loudly with the available versions rather than emitting empty notes, and the heading contract it depends on is covered by tests.
- Added a CI gate that verifies the application version is single-sourced from `package.json`, failing with the exact file and line when a version literal is hardcoded elsewhere; historical records such as changelogs, release notes and the lockfile are allowlisted since they must retain literal versions.
- Added a CI gate that packs the production package, installs it into a clean directory with production dependencies only, and fails if any native Node addon is present. Checking the packed tarball alone cannot detect this, because the tarball contains no installed dependency tree.
- Added a SQLite behavioural contract test suite pinning value conversion, transactions and savepoints, conflict handling, `RETURNING`, foreign keys, persistence across reopen, read-only access, and the prepared-statement surface, so the forthcoming database driver change can be verified against known-good behaviour rather than assumed safe.
- Added independent schema versioning for the application database and each per-project database via `PRAGMA user_version`, recorded in the new `server/db/schemaVersion.ts` module.
- Added a downgrade guard to both database boot paths: a database reporting a newer schema version than the running build now aborts with a message naming the file, both versions, and how to recover, rather than being opened and mutated.
- Added a one-time notice when opening a pre-0.5.0 database that carries no version marker, explaining that such databases are development data, are not migrated, and can be deleted to start clean.
- Established cross-platform config-directory resolution tests covering Windows `%APPDATA%`, Unix `XDG_CONFIG_HOME`, and the `LOOPTROOP_CONFIG_DIR` override, ensuring consistent behavior across all platforms.
- Established the first continuous integration workflow at `.github/workflows/ci.yml`, enforcing lint, typecheck, test, build, clean-tree verification, and production dependency audit on every push and pull request to main.
- Configured the CI matrix to require the declared toolchain — Node 24.15.0, npm 11.12.1 — on Ubuntu, macOS and Windows alike, with non-blocking lanes on the newest Node 24 patch and on Node 26 to surface upstream and platform-specific issues before the first release.
- Added `engines.node` constraint requiring Node 24 or later to declare the minimum supported runtime before the first public release.
- Added `.nvmrc` pinning Node 24 for automated tooling and CI.
- Added `packageManager` field to record the tested npm version.
- Added the `looptroop` executable with `setup`, `start`, `stop`, `restart`, `status`, `open`, `logs`, `doctor` and `clean`, plus a launcher written in ES5 without dependencies so that a too-old Node prints the required version and how to install it, rather than a syntax error from the modern entry point it was about to load.
- Added a process start identity that `stop`, `clean`, the instance lock and the development preflight all use to tell a running LoopTroop process from a stranger that inherited its process id: the pid together with the kernel's start time for that pid, read from `/proc` with the boot id on Linux, `ps -o lstart` on macOS and `StartTime` on Windows, and hashed so nothing ever prints a boot id. A platform that cannot answer yields "unknown", never a match.
- Added an exclusive single-instance lock per configuration directory, recording the holder's process identity as well as a heartbeat. Identity settles the question on the same host, so a recycled pid is recognised as stale immediately, and a daemon whose timers slept through a suspended laptop is not mistaken for an abandoned one. Reclaiming a lock replaces the abandoned record atomically under a claim scoped to the nonce being replaced, so the path is never momentarily free and no number of processes reclaiming at once can produce two winners.
- Added a readiness handshake, so `looptroop start` reports success only once the daemon is answering on its port with the instance identity it wrote, rather than when its process was spawned. A start that never becomes ready fails with the refusal the daemon recorded, or the tail of the daemon log when it recorded none, instead of a bare timeout.
- Added browser sign-in over a single-use code: `looptroop open` mints one, carries it in the URL fragment — which browsers never send in a request line, so it cannot land in an access log, a proxy log or a `Referer` — and the interface exchanges it for a 12-hour `HttpOnly`, `SameSite=Strict` session cookie scoped to `/api`. The code is spent on first use, so a shared or re-opened link buys nothing.
- Added a separate bearer token for scripts, accepted only as a header. It is persisted in the daemon state file, which is created owner-only *before* the atomic write so it is never briefly world-readable, and it is redacted from `status --json`. Sign-in codes are minted on demand behind an authenticated route rather than once at startup, so `start` and `open` fetch a fresh single-use link over HTTP and the daemon never writes a usable credential anywhere durable — a detached daemon prints no sign-in URL at all. `/api/health` is the sole unauthenticated route and reports the instance identity, so `status` and `doctor` can confirm they reached this daemon rather than a process that inherited its process id, without holding a credential for it.
- Added an OpenCode supervisor that adopts a server already answering on the configured address or starts its own, and records in the daemon state file which of the three outcomes it was — adopted, started, or given up on — together with the reason when there is one. `stop` and `clean` shut down only servers LoopTroop started.
- Added daemon log rotation, bounded while the daemon runs rather than only across restarts, since a detached daemon is designed to be started once and left alone.
- Added an update check that asks the registry at most once a day and prints the upgrade command for the way this copy was actually installed — npm, Homebrew, Scoop, Chocolatey, a container image or a repository checkout — inferred from where the files live and recorded so it is decided once. Anything ambiguous is reported as unknown with a pointer to the documentation, because the wrong upgrade command is worse than none: it installs a second copy somewhere else and leaves the running one untouched.
- Added `looptroop doctor`, which reports the Node version against the supported floor, the configuration directory and its permissions, database schema compatibility for both the application and per-project databases, whether the configured port is free and who holds it if not, the OpenCode binary and its version, the state of the OpenCode server the running daemon depends on, and GitHub authentication. `--json` emits the same findings, with the version numbers behind a schema verdict attached, for scripts. Every probe that shells out is bounded, so the command someone runs to diagnose a hang cannot become a second hang, and a command that hangs is reported as such rather than as missing — which used to send people off to install a tool they already had.
- Added `looptroop setup`, a guided first run for an install that can otherwise do nothing: it has no repository to work on, and the interface behind it refuses every request without a sign-in link, both facts previously discoverable only from the documentation. It asks the three questions that cannot be inferred — which repository, where LoopTroop's own ignore rules may be written into it, whether to open a browser — reports where the settings, database and log live, and can be re-run with any step declined. It attaches the repository root rather than whatever subfolder was typed, so a second run cannot produce a duplicate under another name, and it attaches through the running daemon's API rather than the database the daemon holds open. Run from a pipe or from CI, where a prompt with nothing behind it is a hang, it reports instead of asking; `--yes` takes every default. Its exit code distinguishes a step that was asked for and failed from one that was declined.
- Added a recorded reason for a refused start. A database this build cannot open makes the daemon exit and takes everything it knew with it, leaving a non-zero exit code and a log file nobody mentioned — and the same start fails the same way every time. The refusal is written where the state file would have gone, so `start` prints it instead of a log tail, `status` says why nothing is running, and `doctor` reports it as its own check with both schema versions attached. It is re-checked before being reported, so a refusal already fixed stops being news, and only a schema incompatibility is recorded: transient failures are already reported while the user is watching, and an arbitrary error string could carry anything.
- Added `looptroop clean`, which finds abandoned ticket worktrees, stale locks and orphaned OpenCode servers. Listing is the default and `--apply` is required to act, because neither a path nor a process id is evidence: a directory can be restored from a backup or simply be where somebody put their own work, and a number in a file written days ago may by now belong to anything on the machine, including something a person is using. Removal therefore needs proof. A worktree must carry an ownership marker naming that exact directory in that exact project — written where the ticket's own ignore rules already exclude it, so it never appears as an untracked file — and a marker copied elsewhere authorises nothing; anything unmarked, including every worktree predating this change, is listed with the reason and left to be removed by hand. Beyond ownership, a worktree is kept when it holds uncommitted or untracked changes, has unpushed commits, has a branch with no upstream, or was touched recently, which is what stops a worktree being born from looking like one that was abandoned. An OpenCode server is signalled only while its recorded start identity still matches, re-checked immediately before any escalation, and a platform that cannot answer reads as "do not signal" rather than as a match.
- Added a per-project choice of where LoopTroop's ignore rules are written when a project is attached: the repository's own `.gitignore` (the default, so clones and worktrees inherit it), this clone's `.git/info/exclude`, or nowhere at all for a repository with a policy about generated rules. The answer is stored, so reattaching honours it. Rules are appended, leaving an existing file's content, order and line endings intact and never repeating a rule already present.
- Added the same guarantee to ticket worktrees, applied through the shared `.git/info/exclude`. A worktree is a separate checkout that `git add -A` runs in, and a repository `.gitignore` only reaches it once committed, so until then LoopTroop's own runtime directories would have been staged onto the ticket's branch. A `.gitignore` inside the worktree would instead leave an unexplained file in a checkout meant to hold exactly one ticket's changes.
- Added a published-package verifier that asks npm what it would pack and checks that list against what the manifest promises: every `bin` and `main` entry resolves inside the tarball, the documents a redistributed package must carry are present, and nothing from the working tree rode along. It runs in CI and on `prepublishOnly`, so a release cannot go out with a tarball that fails it.
- Added a release smoke test that packs the package, installs it globally into a throwaway prefix on Linux, macOS and Windows, and drives a whole session from an empty directory: metadata commands, `doctor --json`, start, the interface and its hashed assets, the code-for-cookie exchange and its replay refusal, status, restart, logs, `clean` refusing while the daemon is up, stop, lock release, and no surviving child processes. Two standing rules are asserted rather than assumed: the daemon state file stays owner-only, and neither the API token nor a sign-in code reaches the log.
- Added a test that runs a full session from an installation directory the kernel enforces as read-only, which is what a global install on a shared machine is. It checks both failure modes: a write beside the bundle that stops the daemon starting, and one that is caught and swallowed, leaving the daemon silently degraded. Where no enforceable read-only mechanism exists the run reports that it verified nothing rather than claiming a pass, and in CI that counts as a failure.
- Added a signed-out screen that replaces the interface once the daemon refuses this browser's session, detected from a single `401` watch rather than a rule each query function has to remember. It names `looptroop open` as the remedy and never prints a sign-in link, since such a link carries a live single-use credential that would then appear in any screenshot of the screen.
- Added a lock contention test that releases five real processes from a barrier onto one crashed run's lock, and asserts exactly one of them ends up holding it. The dangerous window sits between two file operations, so no single-process test can enter it.
- Added an adversarial cookie test that runs a second loopback server, has it capture this daemon's real session cookie, and replays it bare, page-shaped and no-cors-shaped. It asserts the capture succeeds, which is honest about the half no server can prevent, and that every replay is refused while same-origin traffic, the development origin, bearer-token scripts and the public health endpoint all still work.
- Added a toolchain pin that installs the npm version named in `packageManager` before any `npm ci` in CI and then asserts `npm --version` reports it, since a global install landing outside `PATH` otherwise leaves the old npm in place and passes silently. The version is read from the manifest rather than repeated in the workflow. The Node 26 lane is deliberately left unpinned, because the npm bundled with it is part of what that lane exists to warn about.
- Added a release-state resolver that decides where a release stands as a pure function of what can be observed: whether this push changed the version, where the tag points, whether a GitHub Release exists and is still a draft, and what the registry holds under which dist-tag. Every job in the release derives its behaviour from that one resolution, so a half-finished release cannot mean one thing to the job that stopped and another to the job that resumes it. The load-bearing rule is that the tag is written last and no single marker means "done": "complete" is the conjunction of every channel, so a tag on its own can never be read as a finished release.
- Added a release pull request workflow that raises the version rather than asking someone to. It writes the new version into the manifest, both lockfile fields that carry it, and the changelog heading, archives the release notes under `.github/releases/`, and opens a pull request whose merge is the act that releases. The version is raised in one place and derived everywhere else, so the four files cannot disagree.
- Added a release manifest recording the version, the commit, the tarball's SHA-256 and the sha512 integrity npm will publish under. Every downstream job verifies the artefact it received against that manifest before doing anything irreversible with it, so a substituted tarball is caught before it is published rather than after.
- Added a post-publish registry check that re-reads npm's own `dist.integrity` for the version just published and fails the release if it differs from what this build produced. The registry is polled until the version becomes visible, because a publish that has succeeded is not immediately readable. The comparison is deliberately against `dist.integrity` and not `dist.shasum`, which is a SHA-1 of different bytes and could never match.
- Added dist-tag assertions to the publish, so a stable release is what `npm install -g looptroop` resolves to and a release candidate is not. npm tags every publish `latest` unless told otherwise and infers nothing from a `-rc` suffix, so a candidate that took `latest` would silently become what everyone installs; the release now refuses to finish in that state instead of leaving it to be noticed.
- Added tests for the release resolver covering the states a real repository passes through, including the two that a naive reading gets backwards: an ordinary push whose tag legitimately sits on an earlier commit is not damage, and a version already published under bytes this build did not produce is not something to retry.
- Added a container smoke test that builds the image from the packed tarball and drives it the way a user would, on `linux/amd64` and `linux/arm64` natively rather than one of them under emulation. Everything it asserts happens inside the container over `docker exec`: the daemon binds the container's own loopback on purpose, so a test that published a port and talked to it would be exercising the escape hatch instead of the default anyone gets. It covers what only a running image can show — that the daemon reaches Docker's own `healthy` verdict, answers an authenticated API call and refuses an unauthenticated one, runs as uid 1000 with an owner-only configuration directory on a named volume, carries a working `git` and `gh`, ships no source tree beside the installed package, leaks no token or sign-in link into the container log, survives a restart, is usable with a bind-mounted checkout owned by another uid, and exits on `SIGTERM` rather than being killed once the grace window runs out.
- Added OCI labels to the image, with the version and the commit passed in at build time so an image can say exactly which build it is once it is running somewhere. The smoke test asserts every one of them is populated, because a label that silently went empty is only ever discovered when someone is trying to debug a container and cannot tell what is in it. The `source` label is what makes the GitHub container registry attach the package to this repository rather than leaving it orphaned.
- Made the release publish the container image, as a channel that runs beside npm rather than behind it. Each architecture is built on its own native runner from the tarball the release already verified, pushed to both Docker Hub and the GitHub container registry under no tag at all, and only once both exist are they joined into one multi-architecture index and tagged. Nothing depends on the npm channel and the npm channel depends on nothing here, so a broken image cannot leave a published package without a tag, and a half-finished container run leaves unreachable blobs instead of an image that pulls on one architecture and fails confusingly on the other.
- Added the tag rules the container channel publishes under, and a pre-flight that refuses to move a tag it did not write. A release takes its version, its `X.Y` series and `latest`; a release candidate takes its version and `next` and is then required to prove it moved neither `latest` nor the series, because that channel has no equivalent of the npm publish job to refuse it. There is deliberately no bare major tag: `looptroopai/looptroop:0` would change meaning under anyone who pinned it on every minor release. The floating tags follow the dist-tag the release resolver already computed for npm rather than being derived from the version a second time, so the two channels cannot end up disagreeing about which release is `latest`.
- Made every registry read that fails for a reason other than a genuine absence stop the release. An expired token, a name-resolution failure and Docker Hub's anonymous rate limit all fail the same read a missing tag fails, and the two mistakes do not cost the same: reading an absence as an error stops a release that could have continued, while reading an error as an absence is how a published version tag gets overwritten with different bytes. A rate limit is now recognised before anything else, because Docker Hub's own throttling response has been known to mention "not found".
- Added verification of what the registries actually serve, rather than of what the push reported. Docker Hub is read with no credentials at all, because a private repository is inspectable by the account that pushed to it and by nobody else — so an authenticated check would pass happily on a repository from which every documented `docker pull` fails for users. Then the published index is checked to carry each architecture's own build, the tag is pulled the way a user pulls it, and the same smoke test CI runs is pointed at the bytes that came back.
- Made the release notes gain the pull commands only once the image has been pulled and smoke-tested, and made writing them repeatable. The draft exists before any image does, so a draft advertising a pull command would be advertising one that fails for as long as the container jobs are still running — or forever, if they fail. The block is written between markers, so a second run replaces it instead of appending a copy, and a hand-written note beside it survives; a block with only one of its two markers is refused rather than guessed at, since guessing where it ends could delete somebody's text.
- Added a dispatch workflow that republishes the container image for a version that is already released. The release resolver knows how to resume an interrupted publish and an interrupted tag, and models nothing at all about a registry, so once npm and the git tag are done a re-run resolves to "complete" and skips the container jobs — there is no state for it to resume into. The repair builds from the tarball attached to the GitHub release rather than from a checkout, because release assets do not expire and a rebuild from source could differ from what was released without anyone finding out; it verifies that the manifest, the tarball and the tag all belong to the version named before it builds anything, runs in the same concurrency group as the release so a repair cannot race one, and applies the identical tag rules through the identical scripts.
- Extended the release report to the container channel, so a run says whether the image built, which index digest it tagged, whether it pulled, and whether the notes were updated — and the issue opened by a failed release now says which channel to repair and how.

- Made `looptroop stop` ask the daemon to shut down over its API first and escalate through signals only under a time budget, rechecking the recorded process identity at each step so a pid released mid-escalation and handed to something else is reported rather than signalled.
- Replaced the wall-clock waits in the council deadline tests with an injected clock. The tests asserted on elapsed real time, which made them fail under a loaded CI runner; with required status checks, one such flake stalls every merge, and a blanket retry would have hidden real failures instead.
- Declared `esbuild` an exact direct development dependency, since the server build invokes it directly rather than inheriting it from another package's tree. It stays development-only, so the packaged runtime still contains no native addon.
- Added a container image built from the release tarball rather than from the registry, so it carries the same bytes every other channel gets and does not have to wait for the npm publish to succeed first. It ships `git` and the GitHub CLI, because the work LoopTroop does is worthless if it cannot open the pull request at the end, and runs as a non-root user so files written into a mounted project are not left owned by root on the host. OpenCode is deliberately absent: it needs a model provider and credentials that belong to the person running it. The daemon still binds loopback only, which inside a container means the container's own loopback, so the image documents sharing the host's network namespace as the first option and treats binding wider as a deliberate act the runtime already refuses to perform without both an explicit opt-in and a token.
- Taught the installed-package smoke test to accept a tarball instead of always packing its own. The release builds the package once and publishes those exact bytes everywhere, so a test that packs a second copy is checking an artefact nobody will install. A path that does not exist is a failure rather than a quiet fall back to packing, and a tarball handed in by the caller is left in place afterwards rather than deleted as build litter. Passing no argument still packs from the checkout, which is what CI does.
- Ran the release scripts under bare Node instead of a TypeScript loader, because the jobs that need them are the jobs that must not install anything. The detect job decides whether a release happens at all, so it runs before any build with no dependency tree; and the draft job holds the permission that creates releases and pushes tags, so installing a development tree there would run third-party install scripts in the one job that can. Node runs TypeScript directly but does not resolve extensionless imports, so those scripts name each other with explicit `.ts` extensions. TypeScript is still checked by the compiler and by eslint.
- Moved the release in which schema versioning began out of the three messages that stated it literally and into one exported constant. The version gate rejects a literal matching the current version, so `0.5.0` written into a message would have become a release-blocking failure in the very release that reached it — a gate failing on a fixed historical fact rather than on the drift it exists to catch. The constant's file is allowlisted; a stale version literal anywhere else in the server still fails.
- Made `--expected-integrity` optional in the release detector, because the detector must decide whether a build happens before the build has produced an integrity value to compare. The nullable state passes through the resolver and the byte comparison moves to the publish job, which is the one place the registry's own record can be read. "Defer the comparison" and "the bytes are fine" are deliberately different states: the first classifies a finished release as finished, and only the second could let a substituted artefact through.
- Rewrote the README quick start to lead with the global install. It now opens with `npm install -g looptroop` followed by `start` and `open`, names the daemon commands alongside them, and says that starting detaches so LoopTroop outlives the shell. Running from a clone is a subsection for people working on LoopTroop itself, marked as the development stack rather than presented as the way to use the tool, and the requirements state the npm floor beside the Node one.
- Made the build-time container marker outrank the install channel recorded in the configuration directory, unless that record already says `container`. The configuration directory is a volume that outlives any one container and can have been filled by a global npm install before it was ever mounted into one, and the recorded channel is deliberately trusted over detection — so the update notice inside a container would have named `npm install -g looptroop@latest`, a command that upgrades a tree the next `docker run` throws away. The marker is set by the image and by nothing else, which makes it the one piece of evidence here that cannot be stale; it also overrides a hand-written pin, because whatever a user meant to correct, they were not correcting the fact that this is a container. A record that already agrees is returned untouched, so a container does not write to its volume on every command.
- Pinned the image's base to a digest as well as a tag, so two builds of the same commit cannot disagree about what they were built on, and gave Renovate a rule that keeps that digest fresh — the existing rule was scoped to GitHub Actions alone, so a pinned base image would have been pinned to whatever vulnerabilities it had on the day it was written and never updated again. A digest refresh is the same Node on a rebuilt base and lands as an ordinary pull request; a Node version bump does not, because the base is pinned to the floor in `engines.node` and moving it on its own would ship users a runtime nothing in CI ran.
- Documented the image as it actually behaves, in both the README and the Dockerfile header. A bare `docker run` exits at startup rather than serving anything, because OpenCode is deliberately not in the image and a daemon that cannot run a single coding operation is worse than one that refuses — so a run needs either a reachable OpenCode server or the explicit mock mode, and neither is baked in. `--network host` is Linux-only: on Docker Desktop the containers run in a VM, so it is that VM's loopback and not yours. The published-port alternative is `-p 127.0.0.1:3000:3000` and not `-p 3000:3000`, which on a shared network would offer a control plane that executes code to everyone on it. And `LOOPTROOP_API_TOKEN` authorises the wider bind without being the token the API accepts — the daemon mints its own at startup and records it owner-only, so the documentation now says where to read the one that works.

### Fixed
- Fixed the container repair failing its own verification whenever it did the thing it exists for. When a repair adopts an already-published index, that index carries the earlier publish's per-architecture manifests and not the rebuild's — but verification was still handed the rebuild's digests, so the leg comparing them failed by construction. The registry would be correctly repaired and the workflow would go red anyway, leaving the release notes unwritten. The tagging step now reports the manifests the published index actually lists, and verification compares against those.
- Fixed a repair of an old release dragging the floating tags back with it. Republishing 0.5.0 after 0.8.0 had shipped would have written `latest` and `0.5` as part of the repair, so `docker pull looptroopai/looptroop` would quietly serve a version three releases behind — reported as a success. A repair now writes the immutable version tag and nothing else unless it can show the floating tag belongs to that version: npm's dist-tags decide `latest` and `next`, and the series is claimed only by the newest stable release in it. Every floating tag a run does not write is now one it must prove it did not move, which also means a stable release is now checked for leaving `next` alone.
- Tightened what a repair will inherit. An index already on the version tag is now required to carry exactly one `linux/amd64` and one `linux/arm64` manifest, pointing at different bytes, before anything is copied from it; the version and commit labels are checked on every architecture rather than on whichever one the registry listed first; and where more than one registry already holds the version they must agree on the index digest itself, not merely on the set of manifests it contains.
- Fixed the pull request being prepared and then never pushed on a machine whose only git credential is `GH_TOKEN`. `gh` reads that variable; git does not, and prompting is deliberately disabled — so every `gh` call succeeded and the push that followed asked for a password it could not request. This is what a container looks like by default. Git is now pointed at `gh`'s own credential helper when a token is present and `gh` is installed, appended after whatever the machine already configures rather than replacing it, so an existing working setup still wins and nothing is written to disk.
- Fixed the documented container mount, which made an external OpenCode server unable to open the code it was asked to work on. LoopTroop hands OpenCode an absolute path to a worktree under the project, so that path has to mean the same thing to both processes; mounting the project at a tidy `/workspace/project` guaranteed it did not, and every run against a host OpenCode would have failed on a directory that exists in only one of them. The documented mount now puts the project at its own path, with the sidecar alternative named for anyone who wants the tidy one.
- Fixed the container repair being unable to repair the case it exists for. A rebuild of an already-released version does not reproduce its digests — the base image and the package repositories it installs from all move — so where one registry had already received the immutable version tag, the rebuilt image was correctly refused as different bytes and the registry still missing the tag could never be filled. The tagging step now decides by reading the version and commit labels on whatever is already published: where that is this release's own earlier publish, its bytes are the released ones, the rebuild is discarded, and the registries missing the tag are filled from the one that has it. An image that is not this release's stops the run exactly as before.
- Repaired remaining repository-local and machine-specific documentation links after the website and documentation split, and restored the README walkthrough GIF from the standalone Website repository.
- Fixed two leak assertions that could have passed without checking anything. Both compared the daemon's output against the API token with a fallback for the token being absent, and that fallback was a NUL byte — a value that appears in neither JSON output nor a log file. Had the token ever been missing from the state file, "the log holds no API token" would have reported success having searched for something that could not be present. The token is now required for those checks to run and its absence is itself a failure. Nothing was leaking: the assertions were simply not load-bearing.
- Gave the browser-interface test project an explicit time budget. It was the only one of the four that declared none, so it silently took the default five seconds — the tightest budget in the suite on its heaviest workload, since those tests render a real DOM in isolated subprocesses. Renders that take a second unloaded need slightly over five under contention, so on the smallest CI machine the lane failed on whichever test happened to hold the processor when the clock ran out, naming a different test each run while the code was unchanged. A test that is genuinely stuck still fails.
- Fixed the version badge in the application header, which displayed a hardcoded version and would have silently shown a stale number after the next release. It now derives from `package.json`, matching the About dialog.
- Raised the timeout on the Vite dependency-optimization policy test, which parses every file under `src/` and `shared/` with ts-morph and could exceed the default budget when the suite runs fully parallel.
- Moved the OpenRouter routing configuration out of the repository directory into the user config directory. Writing into the installation directory would fail outright once LoopTroop is installed globally, since a global install location is read-only.
- Moved diagnostic report output from a working-directory-relative `tmp/diagnostics/` path into the user config directory, so running the diagnostics command as a global tool no longer scatters report files into whatever directory the user happened to run from.
- Replaced the fixed `.tmp` suffix in `safeAtomicWrite` with a unique per-process suffix. Two processes writing the same target file could previously collide, with one rename clobbering the other's partial write.
- Corrected `.env.example` to document the real default config and database locations rather than repo-relative paths that were never valid once installed.
- Fixed `normalizeFolderPath` in `server/storage/paths.ts` to preserve drive-letter paths on native Windows rather than unconditionally rewriting them to WSL `/mnt/<drive>/...` paths, which broke every git repository lookup and project attachment on Windows.
- Declared `@codemirror/merge` in the Vite frontend dependency optimization list so the YAML diff editor loads reliably in development; the optimizer runs with late discovery disabled, so any production browser dependency omitted from that list can fail to resolve.
- Fixed the interface returning not-found for every page from an installed package. The server module is inlined into bundles at two different depths, and a fixed relative path to the built interface resolved from only one of them — not the one the daemon actually runs. In a checkout the built interface sits under the working directory anyway, so every local run passed and only an install could show it.
- Fixed `looptroop start` failing on Windows after a full readiness timeout with nothing in the log. The detached child decided whether it was the entry point by comparing a module URL against a hand-built one, which cannot hold on Windows, so the child imported itself, ran nothing and exited. It compares filesystem paths now and lets the platform's own rules handle the drive letter, the separators and the escaping.
- Fixed the package's main module starting a server, binding a port and installing signal handlers merely on being imported. Any `import('looptroop')` did all three as a side effect, with no opt-out and no obvious cause when the port turned out to be taken.
- Fixed `stop` deleting the instance lock whenever the daemon failed to answer. Not answering is not not-running: a daemon still opening its database, or wedged, or listening somewhere its state file no longer describes, holds that lock and is alive. Only a lock judged abandoned is now removed, and a held one is named in the error.
- Fixed the OpenCode settings in `config.json` being reported by `doctor` and then ignored by the code that talks to OpenCode, which read the environment directly. A user who pointed the settings file at another port kept talking to the default one while `doctor` health-checked the port they had asked for and called it reachable.
- Fixed the daemon leaving behind a live OpenCode server it had started but that never became ready, with nothing anywhere holding its process id — so the next start adopted the broken server instead of replacing it. Ownership now follows the process handle rather than the server's reported health, and the state file distinguishes giving up from a healthy server someone else started, which it previously recorded identically.
- Fixed the OpenCode record being written only at startup, so a crash and restart moved the server to a new process id and left `clean` hunting the old one. The daemon now updates the record on every change, and declines to write once shutdown has released the file.
- Fixed `doctor` exiting successfully on a machine where the next `looptroop start` would be refused outright for want of the OpenCode binary, and on one where the running daemon's OpenCode server had died — both being exactly the question the command is run to answer. It now weighs whether a server is answering, whether a daemon is relying on one, and whether a start could launch one, and repeats the reason the supervisor recorded when it gave up.
- Fixed `looptroop setup` returning success whatever happened, so `--yes` in a provisioning script read as a clean run when the daemon had failed to start, when it would not answer for its own projects, and when the repository was rejected.
- Fixed `clean --apply` reporting success while an OpenCode server it had tried to stop was still running, and still holding the port the next start wants. A provisioning script read that as a clean machine and moved on.
- Fixed `looptroop clean` failing with a raw database error, and leaving an empty database behind, on a machine where the daemon had never started — the state in which people reach for it. It now treats a missing database, one with no tables yet, and one it cannot read as the same answer: nothing is known to be attached, which is never grounds to delete anything. It also keeps projects whose local data has gone missing, whose worktrees are precisely the debris the command exists to find.
- Fixed the daemon log growing without bound. It was rotated once, just before the daemon was spawned, which bounds it only for daemons that get restarted — and this one is built not to be. The running daemon now rotates by copying aside and truncating in place, which keeps its own append-mode handle valid; a foreground daemon writes wherever the user pointed it and is left alone.
- Fixed a failed update lookup counting as never having been attempted, so a machine that is offline or behind a proxy that swallows the request paid a fresh registry request and its full timeout on every single command. Failures are now rationed to the same daily interval as successes, and the last known version survives untouched.
- Fixed the interface fallback answering non-navigation requests with the interface document: a `fetch` for JSON failed at parse time with no indication where the response came from, and a missing script reported a content-type error rather than the not-found that actually happened.
- Fixed the development preflight sparing a running daemon on the strength of its recorded process id alone. A daemon lost to a crash or a dead battery leaves that number behind for the kernel to reassign, and because a spared process's whole subtree is spared with it, one recycled number landing on a shell could shield every stale development process on the machine — leaving the preflight to clean nothing and `npm run dev` to fail on a port it had just protected. The recorded start identity settles it, and where identity cannot be established the daemon is still spared and the reason said out loud, because sparing a stranger costs a port while killing an unverified daemon takes down a session someone is working in.
- Fixed the sign-in code appearing in the output captured from a foreground daemon, where anything printed is liable to be pasted into a bug report.
- Fixed `doctor` reporting a correctly configured project as unprotected. Its re-check stripped the trailing slash before asking git whether a path was ignored, and a directory-only rule matches nothing that way until the directory exists on disk — so the report was wrong right up until it stopped mattering.
- Fixed the version-single-sourcing gate failing on the update comparator's own test fixtures, which must name concrete versions on both sides to prove anything. The exemption is scoped to that one file, so a stale version literal anywhere else still fails.
- Fixed the single-instance lock admitting more than one daemon under real contention. Stale recovery moved the abandoned lock aside, inspected it, and put it back if it turned out to belong to a live daemon; between the move and the restore the canonical path did not exist, so a third process could take it exclusively and start a daemon, which the restore then wrote straight over. Five contenders racing one crashed run's lock produced two or three winners in seven rounds out of ten, each believing it owned the same databases and worktrees. Recovery now stages the replacement under a unique name and renames it into place, and every mutation of the lock goes through one claim.
- Fixed the claim serialising recovery expiring a claimant that was still running. A claim older than thirty seconds was taken over on age alone, so a daemon suspended mid-recovery — a laptop asleep, a starved container, a debugger stop — lost its claim to the next start; when it resumed it finished its own conversion, and two live processes each held the lock. Two further faults compounded it: a claim was judged abandoned while briefly empty between its exclusive creation and its first write, which is a window every claimant passes through, and releasing a claim deleted the path without checking it was still the claimant's, so a process whose claim had been taken over removed its successor's on the way out. A claim now carries a nonce and its owner's start identity, is never expired on age while its owner is provably the same live process, is re-verified immediately before the lock is replaced, and is released only by the attempt that created it. Age still decides for a claim from another machine or one whose owner cannot be identified at all, since honouring an unidentifiable claim forever would let one crash wedge every later start.
- Fixed the same window on the lock file itself, which is where it did the real damage. A lock is created exclusively and written a moment later, so between those two syscalls it exists and parses as naming nobody — and a lock naming nobody was converted on the spot, no questions asked. A contender arriving in that window took the lock out from under the process that had just legitimately won the exclusive create, and both ran. This is the fault that produced two winners in the five-contender race on a loaded runner, where being descheduled between two syscalls is unremarkable. The record is now staged under a unique name and renamed into place, so the canonical path goes from absent to complete with nothing observable in between; and because a lock written by an older build or by a writer killed mid-write still lands unreadable, a lock that names nobody is now left alone until it has been that way longer than writing one takes, rather than being converted immediately or honoured forever. Also fixed `stop` reporting a starting daemon as not running and deleting its lock: an unreadable lock was reported absent, and the removal it then attempted named a sentinel owner that could never match, so the file was left behind either way. It now says the lock exists but does not yet name an owner and leaves it in place, and clears it once it is old enough to be debris.
- Fixed process identity being unverifiable on Windows in hosted CI, where the lookup costs a PowerShell start and intermittently exceeded a bound shared with a `/proc` read. Because "cannot verify" must never be read as "not running", a suspended daemon looked unverifiable and an expired heartbeat was enough for a second daemon to reclaim a lock its owner still held. Windows now gets its own bound, a query that also answers for processes owned by another user, and tolerant parsing of the reported start time.
- Fixed the daemon releasing its lock and state while the OpenCode server it owned was still alive. Termination signalled the child and returned without waiting, so the next `looptroop start` could take the lock while the previous OpenCode still held its port — where the new daemon adopts it as somebody else's server and nothing ever stops it. Termination is now awaited under a budget and escalates to a forced kill before ownership is given up.
- Fixed the restart policy counting deaths rather than attempts, which inverted it: a server whose relaunch failed outright was marked degraded after one try, while one that restarted cleanly and crashed again got the full three — and the first case is the one where retrying helps. Failed launches and failed health checks now each cost one attempt of a bounded three, the daemon's state is updated after every attempt, and a shutdown cancels the loop immediately.
- Fixed `looptroop start` leaving behind the process it gave up waiting for. A readiness timeout was reported and nothing more, but that child is a real process holding the single-instance lock, and it may finish booting seconds after the CLI has said nothing started — leaving a daemon on a port nobody printed that the next start refuses to replace. The start now ends that child under a budget and clears the lock and state it left, both scoped to its pid and instance so a start that raced this one and won keeps its record. Identity is re-checked against a token taken at spawn, since a minute is long enough for a pid to be reissued, and where identity cannot be established the process is left alone and the user is told where to look.
- Fixed the host guard accepting any loopback request that arrived without an `Origin` header, which is exactly the shape a cross-port `<img>`, a no-cors `fetch` or a `window.open` produces — session cookie included. Such requests are now accepted only when the browser vouches for the origin through a header page script cannot forge and that, unlike a site, counts the port. The check applies only to callers leaning on the ambient cookie; a script holding the API token never needed the browser's word.
- Fixed the read-only installation check failing for the wrong reason and passing for the wrong one. `sudo -E` keeps the environment but still replaces `PATH` with sudoers' `secure_path`, so the installed launcher resolved the runner image's Node 22 rather than the pinned 24.15.0, exited in milliseconds, and the version mismatch was read as a read-only failure. The interpreter floor is now checked explicitly. The verifier also bound a fixed port, so a machine already running a daemon produced a pass from somebody else's process, and a survivor of a failed run was left holding the lock; it now takes a kernel-assigned port, matches the health response against the state file it wrote, reaps what it started, and prints the start output and daemon log with nonces and tokens redacted before cleaning up.
- Fixed CI resolving the toolchain rather than pinning it. `node-version: 24` selects the newest patch, so the version `engines` promises was tested on Linux alone while macOS and Windows ran whatever was current that week; and every `npm ci` used the npm bundled with the runner image — 10.9.8 on Ubuntu — rather than the 11.12.1 the repository declares, which is the resolver and lockfile reader differing from what a developer runs.
- Fixed the installed-package smoke test proving the session cookie worked by sending it the way no browser does. It presented a bare cookie with no browser context, which the new same-origin guard correctly refuses, so a test written to show the sign-in path working could only report failure. It now sends what a browser sends, and additionally asserts the case the guard exists for: the same cookie, offered as another loopback port would offer it, is turned away.
- Fixed the lock identity tests sampling process identity once and treating the answer as a property of the platform. `readProcessStartToken` returns null both where a platform cannot report start times and where the lookup simply did not answer, and on Windows it answers by starting PowerShell — which a loaded runner can push past its bound. A sample that came back null sent the test down its no-identity branch while the implementation, asking again microseconds later, got a real token: the two disagreed and the assertion failed, on the blocking Windows lane, with the advisory Windows lane passing on the same commit. Identity is now resolved once before any test branches on it and retried so a single slow lookup cannot decide it, and the value is then relied on rather than re-read — the lookup caches this process's own pid, the one pid whose token cannot change while we are the one asking, and the tests share that module with the implementation, so both sides now answer from the same cache by construction. Where a claim names another process, whose token is deliberately never cached, a failed lookup is asserted as the documented age-based fallback instead of its opposite.
- Fixed the multi-process lock test being able to fail without an exclusion failure. A winner held for a fixed quarter-second, so five processes on two cores could leave a contender descheduled past the release, and its perfectly legitimate acquisition afterwards read as a second winner. Winners now hold until every loser has reported, the assertion checks directly that no two hold intervals overlap rather than only counting winners, and a failure prints what each contender did.
- Fixed the log projection test exceeding the shared 20-second budget on Windows. Its three hundred appends are what the pagination assertions are about and cannot be reduced, and on a hosted Windows runner the per-write filesystem cost makes the same eight tests take thirty-seven seconds against one and a half here. The budget is raised for that one test rather than the whole project, and deliberately not by retrying a test that is not flaky.
- Fixed a required check being able to name a lane that cannot fail. Advisory lanes run under `continue-on-error` and report success however they went, and their job names differed from the blocking lanes' only by a version string — so one commit's required `Test (windows-latest, Node 24)` could become the next commit's advisory lane and go on reporting success forever. Advisory lanes now carry that word in the name branch protection matches on.
- Fixed the Windows test lane failing on a different innocent test almost every run. Two causes, both of them the test runner being told the machine is bigger and the work lighter than either is. The worker pool was a hardcoded six, which is comfortable on a developer machine and oversubscribes a four-core runner, so tests crossed their timeout for want of a CPU rather than for any defect of their own — three jobs on one commit produced three disjoint sets of timeouts, none in the files that commit touched. And a set of tests that drive the real database and real git worktrees had been filed into the bucket documented as pure logic, which is a shared-worker thread pool carrying the tightest budget in the suite. `createInitializedTestTicket` spends nine synchronous `git` spawns per ticket before an assertion runs; a synchronous spawn blocks the whole thread, and Windows has no `fork()` to make process creation cheap. Measured on a hosted runner, four of the five slowest files in that bucket were these, led by one spending 47.8 seconds against a 15-second per-test timeout. The pool now sizes itself to the machine and leaves a core for the process supervising it, and those tests run in the integration bucket, where each gets its own process and the budgets written for that workload. Neither is a raised timeout on a test that was never slow, and no lane retries.
- Fixed the release PR workflow being unable to commit the release it had just prepared. The bump archives the notes to a new file under `.github/releases/`, and the commit named its four paths as a pathspec — which Git resolves against paths it already knows, so a file that has never existed fails the whole commit with `did not match any file(s) known to git`. The first release PR would have stopped at that step, and so would every one after it. The four files are now staged by name first and the commit is still restricted to exactly them, so nothing a previous step left in the index rides along and nothing is ever added wholesale.
- Fixed the release's read-only installation gate being unable to pass. Bind-mounting needs a privilege the ordinary runner user does not have, and the release invoked the verifier as that user while also setting the flag that makes an unavailable mount a failure rather than a skip — so the check could only fail, and it gates the publish. CI's own invocation of the same script already had the privileged form; the release now matches it, with the interpreter resolved before elevation because the sudoers policy replaces `PATH` and would otherwise select the runner image's Node rather than the pinned one.
- Fixed the requested version being substituted into the release PR workflow's shell source at three steps rather than read from the environment. Workflow expressions are expanded before the shell sees the script, so a version string carrying shell metacharacters would run as those steps' own commands — and a later step in the same job holds the token that pushes branches and opens pull requests. Every other step already took the version through the environment; these three were the exceptions.
- Fixed the release's draft-resume path trusting a string. Resuming onto an existing draft compared only the attached manifest's integrity field and never looked at the attached tarball, so a draft carrying this build's manifest beside another build's tarball — or beside no tarball at all — was accepted and published. It now requires both assets to be present, downloads them, compares every manifest field including the commit, and hashes the downloaded tarball against it; a mismatch stops the release instead of publishing bytes nobody verified.
- Fixed `--out` and `--registry-integrity` being unusable in the release manifest and artefact-verification scripts. Both discarded arguments beginning with `--` and counted what remained as positionals, but a flag's value is not a flag: the path or the integrity string was counted as one positional too many, so every invocation using the flag the script documents was rejected with the usage message. Values are now excluded by position. The manifest tool also shortened its closing output path by slicing the repository root's length off the front whether or not the path was inside the repository, so writing to a staging directory elsewhere reported having written a file in the checkout; it now shortens only what genuinely is inside.
