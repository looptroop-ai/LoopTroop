# Changelog

All notable changes and official releases for LoopTroop are documented here.
Unreleased changes appear first and represent commits that have not yet been included in a versioned release.

---

## Unreleased

> Changes merged since the last versioned release that have not yet shipped in a tagged version.

### Summary
- Every user action that skips something now takes an optional reason: an interview question, all remaining questions at once, an answer marked skipped at approval, an approval with known coverage gaps, a Manual QA round, finishing without merging, and cancelling a ticket.
- The model that fills in skipped interview answers can now read why they were skipped, instead of guessing blind. No other model sees those reasons.
- A `Skips` panel in the Full Log shows the whole trail for a ticket: what was skipped, when, by which action, and what the reason said at the time.
- Finishing a ticket without merging now asks for confirmation instead of ending the ticket on one click.
- A cancelled ticket keeps its reason even when its artifacts are deleted with it.
- The installation documentation now shows how downloads change over time, with source, date range, interval, metric and chart controls.
- A model that stops to ask you something no longer freezes the app or stalls the run. The question opens at the top of the ticket, waits five minutes by default, and then refuses itself so the run carries on. If you engage with it, the clock stops and it waits for you.
- Two new settings decide whether a model may stop a run to ask you a question, and how long that question waits. Both can be set for the whole configuration, for one project, or for one ticket.
- Waiting for you no longer costs a step its working time, and no longer counts as implementation time either. A step can take its full timeout plus however long it spent waiting on an answer, and the ticket's delivery time now separates the two.
- Any step can ask, not just the five it happened to be allowed in. The interview is excluded, because it asks its own questions, and so are the steps that only reformat text.
- Browser launching, release checks and rendered third-party text now keep externally controlled values out of command shells and executable markup.
- The names your scripts read — API routes, live-event names, and the check names in `doctor --json` — are now written down in a test. None of them can be renamed without that showing up as a deliberate edit in review.
- A project that ships its own `opencode.json` keeps it — in git as well as on disk. Setting a step cap used to replace that file for the whole coding run, commit LoopTroop's version onto your branch, and delete the file afterwards, taking the project's MCP servers, providers and other agents with it.
- Startup now genuinely finishes writes that a crash interrupted, and refuses the ones it cannot vouch for. It never replaces a file that is already there, and it never puts back a JSON document that stops mid-sentence.
- Manual QA baselines and drift receipts are now written durably, and startup can recognise and finish one that a crash interrupted.
- Opening a different ticket now starts that ticket's workspace clean. Answers, drafts, skip reasons, open dialogs and error notices used to belong to whichever ticket you opened first, and an answer typed for one ticket could be saved onto another. What you were still typing survives the switch too, saved against the ticket you typed it for.
- Live logs stop working against themselves. Every arriving line used to make the panel ask the server for the page that line had just arrived on, so the busier a ticket got the more work each line caused. Watching a run is now quiet, streaming output follows itself down the screen instead of appearing to freeze, and the log shows what it was dropping: a cancelled ticket's history, a per-model tab's output, and each attempt of a retried phase on its own rather than merged into one.
- The interface now answers the keyboard and says what it is. Escape dismisses the dialog or dropdown you opened rather than leaving the ticket, ticket cards can be opened without a mouse, overlays name themselves and keep focus, and icon-only buttons have names. Filters reset completely, saved feedback survives the save, a failed refresh stops spinning, a failed answer edit says so, and renaming an environment variable no longer destroys another one.
- Which statuses mean a ticket is finished, and which hold a project's one execution slot, are now recorded once in the workflow table. The finished answer used to be written out by hand in sixteen other places — Delete, Cancel, the list of actions a ticket offers, the pulsing card, the five-second polling, the duration clock and the live activity strip each carried their own copy — so adding a status meant finding all of them.
- Helpers that had drifted into copies across the codebase are now written once. Terminal escape sequences are stripped the same way everywhere, so failure notes no longer keep control characters that the interface would have removed; and a ticket's council roster is locked by order, so reordering it correctly counts as a change to who implements the ticket. Failures reported by the API now read as the error's own message rather than as `Error: message`.
- Types and value lists that both halves of the app have to agree on — the install channel, the git hook policy, prompt-load warnings, bead notes, the prompt timeout kind — now have one definition each instead of one per side. A value added to any of them can no longer compile cleanly on one side and fail at runtime on the other. An execution setup plan naming a git hook policy nobody recognises now says so instead of quietly reading back as advisory validation.
- Command output is capped by bytes, not by characters. A build log full of non-ASCII text could return up to four times the advertised limit, and truncated output now always says it was truncated. The interface also stops shipping a server database module to the browser, and the build fails if one is reintroduced.
- Workflow statuses are now a type the compiler checks, not free text. A typo or an impossible status could previously reach storage and the log, and be filed under a status that does not exist. Model output that stacks transcript speaker tags is also read correctly now — `[assistant][tool] summary: ...` parses where it used to fail.
- A failed request now says what failed. Every error the interface shows carries the status code and the server's own explanation, instead of the same "Failed to …" sentence whether the daemon was down, the session had expired or the ticket was gone. Ticket ids are also encoded properly, so a ticket whose id contains a slash or a colon stops asking the server about a different ticket.
- Every ticket the interface draws is now put into one shape as it arrives, instead of each screen patching up the server's payload its own way. Manual QA fix beads finally show their origin badge and their completion time, which the dashboard had been dropping; the board and the phase timeline agree on bead progress; and an action the server offers that this version does not recognise no longer renders a button that cannot work.
- A tab left open past its session now says so. The live stream cannot report an expired session — the browser gives its error no status — so an overnight tab with nothing running reconnected forever against an API that refused every request, with nothing on screen saying the session had run out.
- Deleting a ticket, or a project, now clears everything the browser was holding for it. Six kinds of cached data survived a delete — phase attempts, Manual QA rounds, AI details, bead lists, bead diffs and per-artifact content — and a ticket id can be issued again, so the next ticket with that id started off showing the previous one's data.
- A request that fails no longer looks like a result that is empty. Bead lists, approval outlines, a phase's version history, per-bead diffs, interview, PRD, beads and setup-plan content, the artifact list and the log panels each drew "nothing here yet" for a server error, so a broken daemon read as work still in progress and nobody retried. Each of those surfaces now says the request failed, quotes the status, and offers a retry. The setup-plan screen no longer reports a failed *request* as a failed plan *generation* and offers to regenerate.
- A council round can no longer finish on a draft nobody scored. Voting used to fall back to the first council member when the scorecard was empty or every score was zero, and the refine step then rewrote a draft that did not exist. An empty reply from the winning model is no longer accepted as a finished refinement either: it is retried, and reported as empty if the retries run out.
- A bead can no longer be marked done by a report that names a different bead, and a stored bead status the scheduler does not recognise no longer stalls the whole ticket in silence.
- Repair notices on model output now describe the artifact that was accepted. A repair attempted on a rejected candidate, or one that never fed the parser at all, used to be reported against whatever eventually validated, which is what raised an intervention warning on output that needed no repair.
- Interview coverage now has to mean what it says, a rewritten interview or PRD has to say what it changed, and a saved interview session is checked field by field before it is restored.
- Manual QA now reads the approved PRD one way instead of three, and the repository inspection it makes mandatory before writing repair beads has to actually be one.
- A bead edit that only changed its PRD references or its context guidance now shows up in the refinement diff instead of being dropped from it.
- A git command that cannot finish now gives up instead of taking the whole app with it. Every `git` and `gh` call has a deadline, refuses to open a credential prompt, and can handle the same large diff wherever it runs. The ones that talk to GitHub no longer block everything else while they wait.
- Opening a ticket can no longer break it. A slow or rate-limited GitHub during a routine page refresh used to move the ticket to Blocked; it is now recorded as an advisory note and retried on the next refresh.
- A renamed file is now delivered as a move rather than as two copies, and a bead commit that fails leaves nothing half-staged behind it.
- Checks that were quietly skipping work now do it: a coverage follow-up budget of 0% really means none, a bead dependency declared in one direction only is rejected instead of running anyway, and a plan approved on one operating system keeps its own commands instead of being rewritten for whoever opens it.
- Git hook validation refuses to run when it cannot undo what the hooks do, and puts the worktree and the staged files back even when a hook fails or the run is cancelled.
- Manual QA evidence survives two people working at once, a typed skip reason survives a reload, and a repaired or retried checklist now says so instead of looking like a clean first attempt.
- `looptroop logs` no longer garbles text. A log with any accented or non-Latin characters in it grew two replacement characters every 64 KiB.
- Cancelling a ticket now actually stops what it was waiting on. The health probes it was in the middle of carried on talking to an unreachable server for their full timeout, and a finished ticket kept its retry bookkeeping for half an hour — long enough for a restart of the same ticket to inherit it.
- Two answers submitted for the same ticket at once can no longer overwrite one another's bookkeeping, whichever way they arrive. The second is refused outright.
- A bead tracker with a damaged line now loses that line, with the file's own line number, instead of crashing a step somewhere else entirely. The line number it reports is the one in the file, not a count of the lines that survived.
- Git hook validation now says when it could not put the worktree back, instead of losing the validation result to an error about the cleanup.

### Added
- Every skip surface now takes an optional reason. Interview questions can be skipped individually with their own reason, or all at once with a single reason for the action. An answer marked skipped at the interview approval screen takes one, as does approving a PRD or bead plan with unresolved coverage gaps, skipping a Manual QA round, finishing a ticket without merging, and cancelling. Reasons are always optional; nothing is blocked for lack of one, and no screen nags about a skip that has none.
- Skip reasons are stored twice, on purpose. The current reason lives on the artifact the surface owns — the answer in `interview.yaml`, the Manual QA summary, the merge report, the ticket's own `cancel_reason` column — which is what the interface reads back. An append-only receipt records the history separately: who skipped what, when, from which surface, and what the reason said at that moment. The two are never inverted, so editing a reason at approval does not rewrite what was recorded during the interview.
- A `Skips` toggle in the Full Log, next to AI details, listing every skip on the ticket with its surface, item, and reason. It spans every phase and every retried attempt, because a receipt from an archived attempt is still a decision somebody made. The counts read as actions and items, so skipping forty questions in one click is one action and forty items rather than forty-one skips. Eight lines are shown at a time and the rest scroll, so the panel cannot push the log off the screen.
- `GET /api/tickets/:id/skips` returns the same trail, optionally filtered by phase or surface.
- Skipping an interview question now records the moment it happened. It previously recorded nothing, which made a deliberate human skip indistinguishable from an unanswered placeholder.
- Undoing a skip is recorded too. Answering a question you had skipped, or clearing an answer during the interview, both update the trail instead of leaving the old decision standing as though it were still current.
- Questions now open in a panel at the top of the ticket, which pushes the workspace down instead of covering it. When several models ask at once, each gets a tab; the countdown appears once, in the panel header, because there is one clock for the whole step. A question on a ticket you are not looking at slides a bar down from the top naming it.
- A bounded wait. When it runs out the question refuses itself and the run continues on the model's own judgment, which is what the tool already does when a person declines. LoopTroop never invents an answer on your behalf.
- Switching between questions, switching model tabs, typing an answer, or pressing Stop timer all do the same thing: the countdown stops, for good. The ticket then waits in Needs Input until you answer or skip.
- The countdown belongs to the step, not to each model. Stopping it in one model's tab stops it everywhere, and another model arriving while it is still running puts it back to the full wait.
- The clock lives on the server. Close the tab, come back two minutes later, and two minutes are gone; reopening the page does not restart it, and nobody watching does not pause it.
- A ticket with a question waiting moves into Needs Input on the board and pulses in its own colour, distinct from the red used for failures. Its underlying status does not change.
- Skipping a question takes an optional reason, in the same box every other skip uses, and it appears in the ticket's Skips panel.
- The Skips panel now says who did the skipping. A question that ran out its wait is filed against the clock with the wait length and the time elapsed, never under your name.
- AI questions and AI question wait, on the Configuration screen, the project form, and a ticket's Advanced section. The two cascade independently, so a ticket can set its own wait while taking the on-off choice from its project. The wait runs from one minute to an hour and defaults to five. Waiting does not use up the step's working time. A ticket that has already started shows both values read-only, with the level they came from.
- Added download history to the installation documentation. The chart records public npm, Docker Hub and GitHub release counters every hour, can show new downloads or cumulative totals, and separates installer-script fetches from the sources included in the download total. History begins when tracking is enabled; the chart does not fill earlier periods with estimates or npm-only data.

### Security
- Closed the two critical and seven high code-scanning findings. Windows opens sign-in links through the URL protocol handler without `cmd.exe`; the published install smoke accepts only the stable and `rc.N` version formats the release tooling can produce; channel checks no longer compile command-line values as regular expressions or mistake uninstall output for an installed channel; ticket links receive URI encoding after protocol validation without changing existing percent escapes; release-note markers and multiline third-party notice cells use context-specific handling; node-manager smoke paths come from fixed manager mappings; and test fixtures no longer use predictable paths under `/tmp`.

### Changed
- The two bead metric shapes are named after what reads them — `CoverageBeadMetrics` and `RefinementBeadMetrics` — instead of differing by one letter. They stay separate on purpose: coverage counts test commands, refinement does not, and the interface never renders that count. The stored `draftMetrics` field is unchanged.
- Terminal escape sequences are stripped by one shared implementation. Bead failure notes and finalisation excerpts went through a version that handled only the 7-bit forms, so 8-bit C1 sequences survived into text the interface had already sanitised elsewhere; all four call sites now use the same superset.
- Error details returned by the API are the error's own message. Twenty-one response boundaries built theirs with `String(err)`, which reads as `Error: something failed` for a thrown `Error` and as `[object Object]` for anything else. Status codes and response keys are unchanged; only the text inside `details` moves. One ticket phase-log line, `✗ Workflow Dispatch`, changes the same way and is visible in the ticket's own log.
- The council model lock compares the roster in order. It previously compared it as a set, which meant reordering the members passed the immutability check even though the first member is the ticket's main implementer — so the roster could be reordered after a ticket started and quietly change who implements it.
- `IgnoreMode`, the API-token header, the bearer-token reader, the constant-time comparison, the process-liveness check, the abort-error predicate, the bounded git diff summary used by Manual QA, the structured-retry prompt and the Drizzle construction each now have one definition instead of two to four. Values, wire format and message text are unchanged.
- `isRecord`, `getErrorMessage` and `normalizeString` are imported from `@shared/typeGuards` at every call site. Thirty-seven local copies are gone, including one in ticket normalisation that accepted arrays as records. Two variants that genuinely differ are kept and documented: the chunk-reload helper, whose callers pattern-match its empty string, and the session-creation helper, which falls back when an `Error` carries an empty message.
- A lint rule now fails the build on a new local declaration of any of those helpers, so the drift cannot return quietly.
- The git hook policy has one mapping. The rename from the older policy names (`validate_explicitly`, `ignore_internal_only`, `use_on_internal_commits`) was written out four times — twice as hand-written boot SQL, once in the migrator the tests cover, once in the SPA — and the two SQL copies are now generated from that migrator. Stored values are unchanged and there is no migration.
- `GitHookPolicy`, `InstallChannel`, `PromptLoadWarning`, `BeadNoteEntry`, `PromptTimeoutKind` and the release details each had a second, independent declaration on the other side of the wire. Each now has one, in `shared/`. JSON payloads are unchanged.
- Unions that existed simultaneously as a TypeScript type, a Zod enum and a chain of comparisons — blocked-error diagnostic kinds and sources, structured failure classes, execution setup workspace-input categories — are now derived from one list each. The workspace-input categories moved next to the git hook policy in the shared code both halves read, so the ticket request schema and the two places the SPA parses a setup plan derive from the same list the server validates against. Literal order, fallback values and error text are preserved.
- The AI-question wait bound, the git hook policy enum, the ignore mode enum and the shared ticket fields are validated from one fragment rather than five. Accepted input is unchanged, including the deliberately different title limits on ticket create and update.
- Command output truncation is byte-accurate. Both command runners computed the remaining budget in bytes and then cut by JavaScript characters, so output containing multibyte characters — a CJK path, box-drawing, an emoji — could exceed the one-megabyte cap threefold. Truncation now stops on a code-point boundary, never emits a replacement character, and always appends the truncation notice; ASCII output is unaffected. The two runners share the append and the SIGTERM-then-SIGKILL process-tree kill.
- The machine ticket context is built in one place. Two route and phase call sites plus the test factories each assembled the same thirty-five-field record by hand and had drifted apart: one dropped the ticket's error message, codes and diagnostics, one skipped the setting-source normalisation, and the missing-iteration-cap fallback was `0` in one and `1` in the other where the rest of the codebase uses the profile default. None of it was reachable, because the consumers read only the identity and model fields — which is why it survived.
- Configuration defaults the interface reads now live in `shared/`. Seven components imported them from a server database module, so the browser bundle carried that module and its transitive imports.
- The client build fails if a `server/` module reaches the browser bundle. It reads rollup's module graph rather than searching the emitted text, which both false-positives on source-map content and false-negatives on an import renamed during bundling.
- A `TicketContext` field added as optional can no longer be omitted by any of the four builders: the field list is checked at compile time against the interface, and every builder is checked against the list by test.
- Terminal escape sequences that end with the 8-bit string terminator are recognised, and a sequence now ends at its first terminator instead of its last. The greedy match could span two sequences and delete the real output between them — a line of a build log disappearing on its way into a failure note.
- Command output keeps multibyte characters that straddle a chunk boundary. A child process emits bytes, and each batch was decoded on its own, so a CJK path, an emoji or box-drawing split across two reads became replacement characters well below any size limit.
- An execution setup plan naming an unrecognised git hook policy now says so, in the warnings the parse returns, so it reaches the screen showing the plan. It previously coerced the value to advisory validation without a word, which is indistinguishable from a plan that asked for advisory validation.
- Workflow phase typing now covers the log writers, session manager, session continuation and skip-receipt writes as well. A stored phase that is no longer a declared status is narrowed at one shared helper with a stated fallback, rather than each boundary spelling out its own chain.
- A workspace profile whose git hook policy cannot be read now says explicit hook validation was skipped for that reason. It previously reported the skip as a policy choice nobody had made.
- Reading the token out of an `Authorization` header no longer slows down as the header grows. The pattern could be made to backtrack, so a long enough header occupied the server for hundreds of milliseconds before the request was even authenticated. Which headers are accepted and rejected is unchanged.
- Workflow phase identifiers are typed. Log emission, artifact storage, command logging, question windows, edit receipts and the machine-facing helpers accepted any string, so a typo or a status that no longer exists could be written to storage and to the log without complaint. Where a phase genuinely arrives from outside — a stored session row, an artifact written by an older build, a compound machine state — it now passes an explicit check with a stated fallback rather than the type being widened back. `UI_STATE`, the bucket the interface's saved view state is filed under, is declared as what it is: an artifact phase that is deliberately not a workflow status. No runtime behaviour or stored value changes.
- Transcript speaker prefixes are stripped the same way everywhere. The interview parser removed every stacked prefix; the structured-output parser and the prompt-echo detector removed only the first, so a line reading `[assistant][tool] summary: ...` still opened with a bracket that YAML reads as a list. All three now strip to a fixpoint, so model output that stacks tags parses instead of failing.




- Overlays now say what they are and keep the keyboard inside them. The Configuration, Prompts, About, Projects, New Ticket and folder-picker windows, and the keyboard-shortcuts overlay, are announced as modal dialogs named by their heading; opening one moves focus into it, Tab stays within it, the page behind it becomes inert, and closing it returns focus where it was. The attributes and the focus handling ship together on purpose: announcing a boundary the interface does not enforce is worse than saying nothing.
- Both dropdowns now hand the keyboard back to the button that opened them however they close — Escape, a selection, or a click elsewhere — instead of dropping it at the top of the page. The one used by the project and appearance pickers also reports whether it is open and which popup it owns, and closes on Escape. It describes itself as a disclosure rather than claiming to open a menu or a dialog, because what the popup contains is up to whichever screen uses it.
- Popups that are drawn outside the page — the project picker, the model list — now count as part of the window that opened them, so the keyboard can reach into one and cannot fall out of the window through it. Opening the project picker moves the keyboard into it rather than into the next field, and closing it hands the keyboard back to the control that opened it. A popup belonging to a window underneath is not treated as part of the one in front.
- Menus and confirmations that manage their own keyboard focus are left to do so. A window no longer pulls the keyboard back to its own first control when Tab is pressed inside a menu opened from within it.
- Icon-only controls that had no name for assistive technology now have one: the folder picker's "go up one level", the emoji search's clear button, and each preset's delete button, which now names the preset it removes.

- Whether a model may stop and ask is now a setting rather than an accident of which tool policy a prompt happened to use. It ships enabled, so an existing install gains the behaviour on upgrade; turn it off in Configuration, per project, or per ticket. Tickets already running when you upgrade keep their old behaviour and never ask.
- A question wait no longer counts against the step it interrupts. Every phase timeout exists to catch a stuck model, and a model blocked on a question is waiting on a person, not stuck. This is what makes Stop timer honest: without it, stopping the clock would only have moved where the run died. This holds in every step that can ask, including those that do not manage a clock of their own.
- Time spent waiting for you to answer is no longer counted as implementation time. A question does not change the ticket's status, so the wait used to be billed as coding — inflating the ticket's active duration and training the delivery estimate on throughput that never happened. It is now recorded separately and shown on its own line when there is any.
- A council member that asked you something and got an answer drafts with steering the other members never saw, and is then judged by members who did not see it either. The vote is now told that a draft was steered, without being told which model wrote it, so following your instruction cannot be mistaken for disagreeing with everyone else.
- The full-screen question popup is gone. It covered the logs, the phase timeline and the artifacts you would want to read before answering.
- PROM10a, which invents answers for skipped interview questions, now receives the reasons as a separate read-only section of its prompt. They are not part of the interview artifact it is asked to reproduce, so there is no field for it to write one back into, and reasons are stripped from the artifact everywhere else — PRD drafting, PRD voting, interview coverage and every downstream prompt see the interview without them. Reasons are shortened to 500 characters where a prompt reads them, because forty skipped questions at the full storage limit is a great deal of prompt spent on notes.
- Finishing a ticket without merging now opens a confirmation carrying the optional reason, rather than ending the ticket on a single click. That dialog, the cancel dialog, and the Skip All dialog all wait for the request to succeed before closing: on failure they stay open, keep what you typed, and show what went wrong.
- The Manual QA waiver box and the skip reason box are now the same component, so both cap at the same length and behave the same way. A waiver still explains one check and a skip still explains the whole round; they are recorded separately and never merged.
- Interview answers now distinguish a person's skip from an automatic AI fill. Both were previously recorded as `ai_skip`, which is why a skip reason had nowhere to display.
- Cancelling a ticket with a malformed request is now refused. It previously fell back to defaults and cancelled anyway, which meant an oversized reason was dropped while the destructive part of the request went ahead regardless.
- Skipping the rest of the interview no longer treats a choice question you answered by picking an option as unanswered. The dialog promises to preserve what is in the batch, and it now does.
- A wire-contract test now pins the three surfaces this project does not control on its own: the 94 API routes, the eight live-event names, and the fifteen `doctor --json` check names. All three are read by things outside this codebase — the interface, users' scripts, the project's own install smokes — and renaming one broke those consumers silently, because a lookup that finds nothing raises no error. The names are listed by hand rather than counted, so changing one is an edit a reviewer sees.
- The live-event names are now declared as a list the daemon broadcasts from, with their type derived from it, instead of a type alone. A contract that exists only as a type disappears at runtime and cannot be asserted on; this makes adding or renaming an event one edit in one place.
- `npm run typecheck` now covers the `tests/` directory, which ESLint already linted but the compiler never saw. It runs as a second project so the application code keeps being checked under its own settings. The three release and installer scripts those tests import are plain ESM for good reasons — `install.sh` runs one with nothing but Node — so each gained a declaration file rather than being pulled into the type-checked build.
- Eleven client tests that touch no DOM moved from the jsdom project to the plain Node one. They were paying for a browser environment, a forked worker and per-file isolation to assert on strings. Membership is by content: `ManualQAView.test.ts` moved, and the `.render.test.tsx` beside it did not.
- Added focused tests for two YAML repairs that had none, ahead of the work that will change them: the type-union scalar repair, and duplicate-key removal where the duplicate is a block scalar. Some of what they record is current behaviour rather than correct behaviour, and says so where that is the case.
- The ticket navigator's width is now remembered, per browser, instead of resetting whenever you open another ticket. Everything inside a ticket's workspace is rebuilt per ticket on purpose; the navigator's width is part of the window rather than part of the ticket, so it is the one thing that deliberately survives the switch, and it now survives a reload too. It is stored once, when you let go of the handle, rather than on every pixel of the drag, and is held to the same bounds on the way in as on the way out — a width saved on a wide monitor cannot take over half a narrow window.
- Two facts about a workflow status are now recorded on the status itself: whether it means the ticket is finished, and whether it holds the project's single execution slot. Both are marks on the phase table, deliberately separate from the board column and the phase group, because those describe where a status is shown rather than what it permits — a status grouped under Done for display reasons should not thereby decide that a ticket can be deleted. Sixteen hand-written copies of the finished answer are gone, across the delete and cancel guards, the list of actions a ticket offers, the archive query, the runtime projection, the two polling intervals, the ticket card, the two log panels, the question banner, the ticket header and the runtime-stall diagnostic's SQL filter. The twelve-status execution band is derived from the same marks instead of being listed a second time.
- The state machine's list of states is now checked against the phase table. It previously agreed with a 34-entry board-column map maintained by hand next to it; that map is gone, and a test asserts the machine has exactly one state per declared phase and no others, which is what the map was implicitly guaranteeing.
- Status labels and descriptions on the client are now built from the phase table itself, so a phase added to shared metadata cannot ship without either — there is no second list to keep in step. Text for a status that is not part of the workflow is asked for through a lookup that can answer "no such status" rather than by indexing a map that would hand back `undefined` typed as a string. The board's own copy of the column type is gone too, and a dead second column map beside it.

- Every request the interface makes now describes its own failure the same way. Nineteen separate error readers — across the data hooks, the four approval panes, the question panel, the folder picker and the ticket header — have been replaced by a single one that always reports the status code alongside whatever the server said. Mutation notices and banners consequently read `Failed to cancel ticket (HTTP 409: Ticket is locked)` where they previously read `Ticket is locked`, or in several places nothing at all. Response bodies are unchanged; only the sentence the interface builds from them moves. A `details` field carrying a field-by-field validation map is now left out rather than printed as `[object Object]` — which is what the question panel showed when an answer was rejected, and what several approval banners showed on a validation failure.
- The approval screens share their common parts instead of carrying four copies each. The editor toolbar, the approve and coverage-fix requests, and the rule deciding which attempt of a phase is on screen are each written once now. The last of those had already drifted: one screen resolved the selected attempt differently from its siblings, and only one of the four reset that choice when the phase changed.
- The model catalog has its own retry count and delay instead of borrowing the live-stream reconnect delay and the OpenCode call retry count. The values are unchanged; retuning the stream no longer silently retunes model fetching.
- Tickets are normalised once, where they arrive, rather than by each screen that reads them. The ticket list and ticket detail queries put every payload into one canonical shape, and every write back into that cache goes through the same function — so a mutation response cannot reinstate the raw server shape for the most-watched ticket. The wire shape is now written down separately from the view model, which is what the compensating casts in five components were standing in for. The list of actions a ticket can offer is a runtime list in the shared workflow table, so the client can check what the server sent against it instead of casting.
- `useWorkflowMeta` reads the shared workflow table directly. It was a query that could not reach the network — seeded from those same constants, never stale, never invalidated — so its fetcher was unreachable and its loading flag was always false. The `/api/workflow/meta` route is unchanged.
- Every `git` and `gh` invocation goes through one runner. Forty call sites had drifted into six variants: most set no timeout, so a credential prompt or an unreachable remote held the daemon thread — and with it HTTP, live events and every ticket — indefinitely; most inherited Node's 1 MiB output ceiling where the established runner used 16 MiB, so the same large diff succeeded in one phase and failed in another. The runner carries a mandatory timeout, the non-interactive git environment, the shared command log and the 16 MiB ceiling, and never throws on a non-zero exit — each caller keeps its own contract for that. Push keeps its two-minute budget and the GitHub permission probe its five seconds.
- Network-bound git and GitHub calls no longer sit on the event loop. `gh` API calls, `fetch`, `ls-remote`, `push` and the remote-branch delete run asynchronously; local plumbing stays synchronous, where a bounded wait is enough. This is what makes ticket start, merge completion, the ticket read and the project-attach probe asynchronous internally; no route, payload or status code changes.
- `doctor` no longer reports the OpenCode CLI as impossible to launch when its version probe merely timed out. The check names are unchanged; the verdict for a slow probe is not.
- `looptroop logs` reads backwards from the end of the file instead of loading the whole log to print fifty lines.
- Retry and session-continuation read the same failure signals. They had their own copies and could disagree about one failure, which decided whether the session survived for the next attempt. Retry now also refuses `request too large`, `payload too large` and `model not found`, which no retry can fix.
- One serialiser for the execution setup plan, shared by the interface and the server, and one reader for a stored Manual QA summary, shared by the pull-request and integration phases.

## 0.5.9 (2026-08-26)


### Summary
- `stop` no longer strands a running LoopTroop it briefly could not reach, leaving it impossible to stop and `clean` free to delete worktrees it was still using.
- Raising the Node floor no longer requires editing branch protection by hand before the change can merge.
- LoopTroop now builds, packages and installs correctly under npm 12, whose install-script blocking and changed `npm pack` output silently broke two release checks.
- Automated dependency updates run again, proposed behind a seven-day maturity delay and two days for security advisories, with only non-shipping lint and test tooling allowed to merge itself.
- Dependency pull requests now arrive with their licence notices already regenerated, instead of failing until someone updated the file by hand.

### Added
- Added a `Renovate notices` workflow that regenerates `THIRD-PARTY-NOTICES.md` on Renovate's branches and pushes the result back. The file records the exact version of every redistributed package and `licenses:check` fails when it is stale, so every dependency update invalidated it; because the hosted Renovate app cannot run `postUpgradeTasks`, each of those pull requests previously arrived red and needed a person to run one command and commit the result. The workflow builds before regenerating, since the generator reads `dist/client/bundled-packages.json` and would otherwise omit every inlined frontend package and write a file that is wrong rather than merely stale. It pushes with `RELEASE_PR_TOKEN` rather than `GITHUB_TOKEN`, because a push made with the latter does not start workflow runs and the required checks would never re-run.

### Security
- Refreshed `brace-expansion`, `postcss` and `@babel/core` in the lockfile, clearing one high, one moderate and one low advisory. All three are transitive development dependencies whose declared version ranges already permitted the patched releases, so no dependency changed — only the versions resolved against them. The refresh is deliberately scoped to those three packages: refreshing the whole lockfile also moves everything else within its range, which would have carried `@opencode-ai/sdk`, `@hono/node-server` and the CodeMirror packages past the maturity delay and the per-package review they are gated behind.

### Changed
- The Scoop channel check now unpacks with the runner's own 7-Zip instead of downloading Scoop's private copy. Scoop fetches that helper the first time it has to unpack anything, and the fetch failed a job outright — an SSL error retrieving the 7-Zip installer from GitHub releases — which is a network hiccup with nothing to do with this repository failing a check about a LoopTroop manifest. The Windows image already ships 7-Zip, so the download is removed rather than retried: a retry would re-run the same fetch against the same flaky path, while this makes it unnecessary. The step asserts `7z` is on PATH first and fails there if it is not, so an image that stops providing it is reported as itself rather than silently leaving the setting pointing at nothing.
- The integration test bucket runs on its own, capped at two workers, on Windows only. The Windows lane has been failing with several unrelated files crossing their timeouts in a single job while the same commit passes in its sibling run — two files hitting the 45-second and 60-second ceilings together in one job, and once a suite taking 861 seconds against a sibling's 413 while every other Windows job in that run was normal. Budgets were already raised from 20 seconds once for this, and raising them again would only move the ceiling; a bounded budget is what keeps a genuine hang failing rather than holding the job for thirty minutes. Part of the cause is a runner nobody controls, and this does not address that — a machine that turns 413 seconds into 861 will still miss a deadline with two workers. What it does address is the self-inflicted share: this is the only bucket combining process isolation with real git worktrees and real SQLite, and three of those in flight on a 4-vCPU runner, each performing thousands of file operations through Defender, is contention this repository chose. It becomes a separate scheduling group rather than taking a smaller share of the existing one because vitest requires a single worker count per group, so a lower cap is only expressible by leaving it — and lowering the shared count would also throttle the jsdom and pure-logic buckets, which are not what is starving. Sequential groups cost wall-clock time on a lane already near 400 seconds, well inside the 30-minute job timeout. Linux and macOS are unchanged.
- The lockfile is refreshed weekly rather than monthly. Renovate's ordinary pass only sees the packages declared in `package.json`; the lockfile holds several hundred more, reached transitively, and advisories against those produce no pull request. That makes the lockfile refresh their only response path and its cadence their exposure window — monthly meant up to thirty days, and did, leaving a high-severity `brace-expansion` advisory open until it was refreshed by hand. It is not daily because a full re-resolve produces a large diff whenever anything transitive publishes, which is most days, and no per-package maturity gate can apply to it.
- `react-virtuoso` is no longer exact-pinned. Every other package inlined into the client bundle carries a caret range, and unlike the other pinned packages nothing depended on this one being exact: `drizzle` is pinned because its stable line still pulls a deprecated `@esbuild-kit`, `esbuild` because `allowScripts` approves install scripts by exact version, and `postject` because it writes into the published binaries. The resolved version is unchanged; only the declared range moved, so newer releases now arrive as reviewed pull requests with the rest of the bundled frontend.
- The Node and npm floors are now grouped as one update across every file that pins them. `node` and `npm` are each pinned in more than one place — `.nvmrc`, `engines.node`, `engines.npm`, `packageManager` and the Dockerfile base image — and Renovate's managers treat those as unrelated dependencies, so a single floor move arrived as five separate pull requests, none of them mergeable alone because each shipped a runtime or a package manager the rest of the repository disagreed with. The previous rule tried to group them on `depType: engines`, which could not work: `.nvmrc` carries no depType and the Dockerfile is a different manager, while `engines.npm` matched and was mislabelled as part of the Node floor. Matching by package name across the three managers groups them correctly; digest-only base image refreshes stay with the container group, since those are the same version on a rebuilt base.
- The dependency dashboard is switched off and no update waits for approval on it. Major versions and the packages that were held back — drizzle, esbuild, the OpenCode SDK, the Node floor and the container base image — now arrive as ordinary pull requests, reviewed like any other change and closed if unwanted. The dashboard held a permanent open issue whose only function was to let a major be requested by ticking a checkbox; making those updates visible as pull requests removes the issue without hiding anything.
- Dependency update rules are now classified by whether a package reaches users, not by whether it is declared as a dependency or a devDependency. That distinction did not hold here: only eight packages are runtime dependencies, while twenty-one devDependencies — React, the CodeMirror and Radix families, TanStack Query, Lucide and others — are inlined into `dist/client` by Vite and ship exactly like runtime code. A rule keyed on `devDependencies` would therefore have auto-merged user-facing frontend changes with no review. Bundled packages now have their own reviewed group, and the description records that each such pull request also needs `npm run licenses:generate` committed onto the branch, because their exact versions are recorded in `THIRD-PARTY-NOTICES.md`, CI fails when that file is stale, and the hosted Renovate app has no way to regenerate it.
- Auto-merge is now limited to an explicit allowlist of lint, test and type-only packages, restricted to patch updates of stable releases. Nothing on the list is inlined into the client bundle, runs in the published server bundle, or emits an artefact users receive, so a green required-check run is sufficient review. Pre-1.0 packages are excluded, since a `0.x` patch can still break compatibility.
- Renovate now proposes updates daily rather than weekly. Weekly creation quietly turned the seven-day maturity rule into a seven-to-fourteen-day one, because a release that became eligible shortly after a Monday run waited for the next. Schedules are also expressed in cron rather than the English syntax, which Renovate has deprecated.
- `@opencode-ai/sdk` now takes the ordinary seven-day delay instead of thirty. The risk it carries is version skew against an OpenCode CLI that users install separately and that Renovate cannot see, which no maturity window addresses; the manual dashboard approval, which is what actually gates it, is retained.
- Security advisories can no longer be swallowed by the rules that hold a package back. `vulnerabilityAlerts` now pins dashboard approval off, so an advisory against an approval-gated package such as drizzle, esbuild or the OpenCode SDK is raised as a fix rather than queued behind a manual tick, and pins auto-merge off so a vulnerable package cannot inherit the allowlist above.
- `esbuild` and the Node floor are now explicitly gated. `esbuild` is exact-pinned against version-keyed `allowScripts` entries that Renovate cannot add for itself, so an unattended bump would leave its native postinstall unapproved; `engines.node` and `.nvmrc` pin the same version as the container base image and are asserted across the workflows, packaging manifests and tests, so they move together or not at all.
- Pull request concurrency and creation rate are throttled while the accumulated backlog is worked through, so the first batch arrives in reviewable order rather than all at once.

### Fixed
- Fixed Windows test failures caused by temporary directories being removed while a child process still held a handle inside them. Tests that spawn `git`, a hook command or any other child into a scratch directory then delete that tree in an `afterEach`; POSIX unlinks files other processes have open, Windows refuses, and the removal throws `EPERM` from the teardown. Vitest reports that as a failing test with a real name and a real assertion, in a file that is working perfectly — a Windows-only signature this repository has chased more than once and never resolved. All 58 such cleanups across 48 test files now go through one helper that gives the removal `rmSync`'s own bounded retry, the same treatment the git fixture helper already had. The options are inert off Windows, so nothing changes on Linux or macOS.
- Fixed `stop` destroying the records of a daemon that was running but slow to answer, which left that daemon impossible to stop for the rest of its life. The health probe gives a daemon two seconds to reply, and a machine under load can exceed that while the daemon is perfectly healthy; the result was reported as "not running", and `stop` deleted the state file on that basis before it had looked at the single-instance lock. That file holds the only copy of the daemon's API token, so every later `stop` took the same branch and never reached the authenticated shutdown it needed, `status` reported nothing running while a process and a lock survived, and `clean` — whose two guards both read that same file — stopped refusing and was free to remove worktrees the daemon was still using. `stop` now distinguishes a daemon that did not answer from one that is not there, and acts on the first only when the recorded start token proves the pid has not been recycled. Where it cannot prove that, the process is left alone and its records are kept, because stranding a working daemon is worse than declining to stop it. `start` and `status` report the same situation instead of claiming nothing is running, `clean` additionally refuses on a held lock so it no longer depends on a single file, and every escalation rung that confirms the process is gone now clears the records — the two that did not were written for a daemon that answers and therefore cleans up after itself, which a wedged one does not do.
- Fixed the install smoke reporting `exit 1` and nothing else when a lifecycle command failed, which is why the defect above was investigated three times as three separate bugs. Failing commands now report their signal or spawn error as well as their exit code, print what the command actually said, and dump the daemon's state, lock, recent log and doctor report at the point of failure with tokens and sign-in nonces redacted. Assertions downstream of a failed `restart` are skipped rather than scored, since a restart that did not happen cannot produce a new instance id and their failures described consequences rather than causes.
- Fixed atomic file writes failing on Windows when another process still held the file open. Every durable write in LoopTroop — settings, ticket artifacts, runtime projections, receipts, the daemon record — lands by writing a temporary file and renaming it over the target. POSIX replaces a file other processes have open; Windows refuses while the handle exists and reports `EPERM`, `EACCES` or `EBUSY` depending on how the holder opened it, and a virus scanner indexing the file that was just written is enough to produce one. That surfaced as a `daemon.json` rename failing an install check outright. The rename now waits out a handle that has not been released, in ten short steps matching the budget already given to directory removal against the same class of lock. The destination is never unlinked first, since that would trade the atomic replace for a window where the file does not exist, and the temporary file is not rewritten between attempts — it is already written, mode-matched and flushed, and only the final step repeats. Errors that will not resolve themselves, such as a full disk, still fail immediately and report themselves rather than the retries. POSIX keeps the bare rename, because it has no such failure.
- Fixed the four required CI checks carrying the Node version in the names branch protection matches on, which made every toolchain floor bump unmergeable. Raising the floor renamed those jobs, so they reported under names nothing required while the required names were never reported at all — and GitHub waits on an unreported required check indefinitely rather than failing it. The result was a pull request showing every check green and a merge button that never unlocked, with nothing on the pull request naming the cause. The required lanes are now named for their purpose rather than their version, so a floor bump changes only the files that pin it. The advisory lanes keep the version in their names, since nothing requires them and the marker that separates a blocking lane from a `continue-on-error` one is retained.
- Fixed the packaging and install checks misreading `npm pack --json` on npm 12, where its report changed from an array to an object keyed by package name. Both readers took the first array element, which is now `undefined`: `verify:package` — a required check — stopped finding the file list, and the install smoke resolved the tarball to the repository root and tried to delete it, surfacing as `EISDIR` rather than as a parse failure. Both now accept either shape, and the smoke aborts loudly when no filename is reported instead of continuing with an empty path.
- Fixed the package managers installed by CI and by the published install smoke arriving unusable under npm 12. npm 12 blocks dependency install scripts by default and *skips* an unapproved one with a warning rather than an error, so `bun` and `opencode-ai` — both of which fetch their real binary from a postinstall — installed "successfully" with nothing runnable behind them, failing several steps later on an assertion that named neither npm nor the blocked script. Each global install now names the single package it approves through `--allow-scripts`, rather than enabling scripts wholesale. The flag is deliberately confined to those steps: npm 12 rejects it outright in a project-scoped install, so the repository's own `npm ci` continues to take its policy from the `allowScripts` field in `package.json`. LoopTroop itself declares no install scripts, so nothing changes for users installing it under npm 12.
- Fixed the published install smoke reporting every channel as broken when the release was fine. Its check on how the daemon obtained OpenCode read `kind`, the discriminant of the supervisor's in-memory status, rather than `status`, which is what `describeOpenCode` writes into `daemon.json`. Nothing else in any leg failed — install, version, doctor, start, the health endpoint, the interface, the refused unauthenticated call, stop and uninstall all passed on all eight legs of the 0.5.8 release — so the only defect was the assertion. A test now pins the field against the code that renders the persisted shape, so renaming the discriminant fails in CI rather than in a post-release smoke.

Artifact-change events contain metadata rather than bodies, but the interface merged them into the full-content cache as `content: null` before refetching; the same broad cache was shared by unrelated historical phases, and request failures were silently converted to successful empty lists. - Fixed the dev stack surviving the death of the backend it exists to run. `tsx watch` does not exit when the process it watches dies — it waits for a file to change, which is what makes it a watcher — so a backend that exited on a fatal error left `scripts/dev-backend.ts`, `concurrently`'s `killOthersOn`, and any process supervisor above them all reporting a healthy stack while nothing answered on the API port. Every job in the release derives its behaviour from that one resolution, so a half-finished release cannot mean one thing to the job that stopped and another to the job that resumes it. The load-bearing rule is that the tag is written last and no single marker means "done": "complete" is the conjunction of every channel, so a tag on its own can never be read as a finished release.

It writes the new version into the manifest, both lockfile fields that carry it, and the changelog heading, archives the release notes under `.github/releases/`, and opens a pull request whose merge is the act that releases. The version is raised in one place and derived everywhere else, so the four files cannot disagree.
- Added a release manifest recording the version, the commit, the tarball's SHA-256 and the sha512 integrity npm will publish under. Every downstream job verifies the artefact it received against that manifest before doing anything irreversible with it, so a substituted tarball is caught before it is published rather than after.
- Added a post-publish registry check that re-reads npm's own `dist.integrity` for the version just published and fails the release if it differs from what this build produced. The registry is polled until the version becomes visible, because a publish that has succeeded is not immediately readable. The comparison is deliberately against `dist.integrity` and not `dist.shasum`, which is a SHA-1 of different bytes and could never match.
- Added dist-tag assertions to the publish, so a stable release is what `npm install -g looptroop` resolves to and a release candidate is not. npm tags every publish `latest` unless told otherwise and infers nothing from a `-rc` suffix, so a candidate that took `latest` would silently become what everyone installs; the release now refuses to finish in that state instead of leaving it to be noticed.
- Added tests for the release resolver covering the states a real repository passes through, including the two that a naive reading gets backwards: an ordinary push whose tag legitimately sits on an earlier commit is not damage, and a version already published under bytes this build did not produce is not something to retry.
- Added a container smoke test that builds the image from the packed tarball and drives it the way a user would, on `linux/amd64` and `linux/arm64` natively rather than one of them under emulation. Everything it asserts happens inside the container over `docker exec`: the daemon binds the container's own loopback on purpose, so a test that published a port and talked to it would be exercising the escape hatch instead of the default anyone gets. It covers what only a running image can show — that the daemon reaches Docker's own `healthy` verdict, answers an authenticated API call and refuses an unauthenticated one, runs as uid 1000 with an owner-only configuration directory on a named volume, carries a working `git` and `gh`, ships no source tree beside the installed package, leaks no token or sign-in link into the container log, survives a restart, is usable with a bind-mounted checkout owned by another uid, and exits on `SIGTERM` rather than being killed once the grace window runs out.
- Added OCI labels to the image, with the version and the commit passed in at build time so an image can say exactly which build it is once it is running somewhere. The smoke test asserts every one of them is populated, because a label that silently went empty is only ever discovered when someone is trying to debug a container and cannot tell what is in it. The `source` label is what makes the GitHub container registry attach the package to this repository rather than leaving it orphaned.
- Made the release publish the container image, as a channel that runs beside npm rather than behind it. Each architecture is built on its own native runner from the tarball the release already verified, pushed to both Docker Hub and the GitHub container registry under no tag at all, and only once both exist are they joined into one multi-architecture index and tagged. Nothing depends on the npm channel and the npm channel depends on nothing here, so a broken image cannot leave a published package without a tag, and a half-finished container run leaves unreachable blobs instead of an image that pulls on one architecture and fails confusingly on the other.
- Added the tag rules the container channel publishes under, and a pre-flight that refuses to move a tag it did not write. A release takes its version, its `X.Y` series and `latest`; a release candidate takes its version and `next` and is then required to prove it moved neither `latest` nor the series, because that channel has no equivalent of the npm publish job to refuse it. There is deliberately no bare major tag: `looptroopai/looptroop:0` would change meaning under anyone who pinned it on every minor release. The floating tags follow the dist-tag the release resolver already computed for npm rather than being derived from the version a second time, so the two channels cannot end up disagreeing about which release is `latest`.
- Made every registry read that fails for a reason other than a genuine absence stop the release. An expired token, a name-resolution failure and Docker Hub's anonymous rate limit all fail the same read a missing tag fails, and the two mistakes do not cost the same: reading an absence as an error stops a release that could have continued, while reading an error as an absence is how a published version tag gets overwritten with different bytes. A rate limit is now recognised before anything else, because Docker Hub's own throttling response has been known to mention "not found".
- Added verification of what the registries actually serve, rather than of what the push reported. Docker Hub is read with no credentials at all, because a private repository is inspectable by the account that pushed to it and by nobody else — so an authenticated check would pass happily on a repository from which every documented `docker pull` fails for users. Then the published index is checked to carry each architecture's own build, the tag is pulled the way a user pulls it, and the same smoke test CI runs is pointed at the bytes that came back.
- Made the release notes gain the pull commands only once the image has been pulled and smoke-tested, and made writing them repeatable. The draft exists before any image does, so a draft advertising a pull command would be advertising one that fails for as long as the container jobs are still running — or forever, if they fail. The block is written between markers, so a second run replaces it instead of appending a copy, and a hand-written note beside it survives; a block with only one of its two markers is refused rather than guessed at, since guessing where it ends could delete somebody's text.
- Added a dispatch workflow that republishes the container image for a version that is already released. The release resolver knows how to resume an interrupted publish and an interrupted tag, and models nothing at all about a registry, so once npm and the git tag are done a re-run resolves to "complete" and skips the container jobs — there is no state for it to resume into. The repair builds from the tarball attached to the GitHub release rather than from a checkout, because release assets do not expire and a rebuild from source could differ from what was released without anyone finding out; it verifies that the manifest, the tarball and the tag all belong to the version named before it builds anything, runs in the same concurrency group as the release so a repair cannot race one, and applies the identical tag rules through the identical scripts.
- Extended the release report to the container channel, so a run says whether the image built, which index digest it tagged, whether it pulled, and whether the notes were updated — and the issue opened by a failed release now says which channel to repair and how.

The configuration directory is a volume that outlives any one container and can have been filled by a global npm install before it was ever mounted into one, and the recorded channel is deliberately trusted over detection — so the update notice inside a container would have named `npm install -g looptroop@latest`, a command that upgrades a tree the next `docker run` throws away. The marker is set by the image and by nothing else, which makes it the one piece of evidence here that cannot be stale; it also overrides a hand-written pin, because whatever a user meant to correct, they were not correcting the fact that this is a container. A record that already agrees is returned untouched, so a container does not write to its volume on every command.
- Pinned the image's base to a digest as well as a tag, so two builds of the same commit cannot disagree about what they were built on, and gave Renovate a rule that keeps that digest fresh — the existing rule was scoped to GitHub Actions alone, so a pinned base image would have been pinned to whatever vulnerabilities it had on the day it was written and never updated again. A digest refresh is the same Node on a rebuilt base and lands as an ordinary pull request; a Node version bump does not, because the base is pinned to the floor in `engines.node` and moving it on its own would ship users a runtime nothing in CI ran.
- Documented the image as it actually behaves, in both the README and the Dockerfile header. A bare `docker run` exits at startup rather than serving anything, because OpenCode is deliberately not in the image and a daemon that cannot run a single coding operation is worse than one that refuses — so a run needs either a reachable OpenCode server or the explicit mock mode, and neither is baked in. `--network host` is Linux-only: on Docker Desktop the containers run in a VM, so it is that VM's loopback and not yours. The published-port alternative is `-p 127.0.0.1:3000:3000` and not `-p 3000:3000`, which on a shared network would offer a control plane that executes code to everyone on it. And `LOOPTROOP_API_TOKEN` authorises the wider bind without being the token the API accepts — the daemon mints its own at startup and records it owner-only, so the documentation now says where to read the one that works.

### Fixed
- Fixed the container repair failing its own verification whenever it did the thing it exists for. When a repair adopts an already-published index, that index carries the earlier publish's per-architecture manifests and not the rebuild's — but verification was still handed the rebuild's digests, so the leg comparing them failed by construction. The registry would be correctly repaired and the workflow would go red anyway, leaving the release notes unwritten. The tagging step now reports the manifests the published index actually lists, and verification compares against those.
- Fixed a repair of an old release dragging the floating tags back with it. Republishing 0.5.0 after 0.8.0 had shipped would have written `latest` and `0.5` as part of the repair, so `docker pull looptroopai/looptroop` would quietly serve a version three releases behind — reported as a success. A repair now writes the immutable version tag and nothing else unless it can show the floating tag belongs to that version: npm's dist-tags decide `latest` and `next`, and the series is claimed only by the newest stable release in it. Every floating tag a run does not write is now one it must prove it did not move, which also means a stable release is now checked for leaving `next` alone.
- Tightened what a repair will inherit. An index already on the version tag is now required to carry exactly one `linux/amd64` and one `linux/arm64` manifest, pointing at different bytes, before anything is copied from it; the version and commit labels are checked on every architecture rather than on whichever one the registry listed first; and where more than one registry already holds the version they must agree on the index digest itself, not merely on the set of manifests it contains.
- Fixed the pull request being prepared and then never pushed on a machine whose only git credential is `GH_TOKEN`. `gh` reads that variable; git does not, and prompting is deliberately disabled — so every `gh` call succeeded and the push that followed asked for a password it could not request. This is what a container looks like by default. Git is now pointed at `gh`'s own credential helper when a token is present and `gh` is installed, appended after whatever the machine already configures rather than replacing it, so an existing working setup still wins and nothing is written to disk.
- Fixed the documented container mount, which made an external OpenCode server unable to open the code it was asked to work on. LoopTroop hands OpenCode an absolute path to a worktree under the project, so that path has to mean the same thing to both processes; mounting the project at a tidy `/workspace/project` guaranteed it did not, and every run against a host OpenCode would have failed on a directory that exists in only one of them. The documented mount now puts the project at its own path, with the sidecar alternative named for anyone who wants the tidy one.
- Fixed the container repair being unable to repair the case it exists for. A rebuild of an already-released version does not reproduce its digests — the base image and the package repositories it installs from all move — so where one registry had already received the immutable version tag, the rebuilt image was correctly refused as different bytes and the registry still missing the tag could never be filled. The tagging step now decides by reading the version and commit labels on whatever is already published: where that is this release's own earlier publish, its bytes are the released ones, the rebuild is discarded, and the registries missing the tag are filled from the one that has it. An image that is not this release's stops the run exactly as before.
- Repaired remaining repository-local and machine-specific documentation links after the website and documentation split, and restored the README walkthrough GIF from the standalone Website repository.
- Fixed two leak assertions that could have passed without checking anything. Both compared the daemon's output against the API token with a fallback for the token being absent, and that fallback was a NUL byte — a value that appears in neither JSON output nor a log file. Had the token ever been missing from the state file, "the log holds no API token" would have reported success having searched for something that could not be present. The token is now required for those checks to run and its absence is itself a failure. Nothing was leaking: the assertions were simply not load-bearing.
- Gave the browser-interface test project an explicit time budget. It was the only one of the four that declared none, so it silently took the default five seconds — the tightest budget in the suite on its heaviest workload, since those tests render a real DOM in isolated subprocesses. Renders that take a second unloaded need slightly over five under contention, so on the smallest CI machine the lane failed on whichever test happened to hold the processor when the clock ran out, naming a different test each run while the code was unchanged. A test that is genuinely stuck still fails.
- Fixed the version badge in the application header, which displayed a hardcoded version and would have silently shown a stale number after the next release. It now derives from `package.json`, matching the About dialog.
- Raised the timeout on the Vite dependency-optimization policy test, which parses every file under `src/` and `shared/` with ts-morph and could exceed the default budget when the suite runs fully parallel.
- Moved the OpenRouter routing configuration out of the repository directory into the user config directory. Writing into the installation directory would fail outright once LoopTroop is installed globally, since a global install location is read-only.
- Moved diagnostic report output from a working-directory-relative `tmp/diagnostics/` path into the user config directory, so running the diagnostics command as a global tool no longer scatters report files into whatever directory the user happened to run from.
- Replaced the fixed `.tmp` suffix in `safeAtomicWrite` with a unique per-process suffix. Two processes writing the same target file could previously collide, with one rename clobbering the other's partial write.
- Corrected `.env.example` to document the real default config and database locations rather than repo-relative paths that were never valid once installed.
- Fixed `normalizeFolderPath` in `server/storage/paths.ts` to preserve drive-letter paths on native Windows rather than unconditionally rewriting them to WSL `/mnt/<drive>/...` paths, which broke every git repository lookup and project attachment on Windows.
- Declared `@codemirror/merge` in the Vite frontend dependency optimization list so the YAML diff editor loads reliably in development; the optimizer runs with late discovery disabled, so any production browser dependency omitted from that list can fail to resolve.
- Fixed the interface returning not-found for every page from an installed package. The server module is inlined into bundles at two different depths, and a fixed relative path to the built interface resolved from only one of them — not the one the daemon actually runs. In a checkout the built interface sits under the working directory anyway, so every local run passed and only an install could show it.
- Fixed `looptroop start` failing on Windows after a full readiness timeout with nothing in the log. The detached child decided whether it was the entry point by comparing a module URL against a hand-built one, which cannot hold on Windows, so the child imported itself, ran nothing and exited. It compares filesystem paths now and lets the platform's own rules handle the drive letter, the separators and the escaping.
- Fixed the package's main module starting a server, binding a port and installing signal handlers merely on being imported. Any `import('looptroop')` did all three as a side effect, with no opt-out and no obvious cause when the port turned out to be taken.
- Fixed `stop` deleting the instance lock whenever the daemon failed to answer. Not answering is not not-running: a daemon still opening its database, or wedged, or listening somewhere its state file no longer describes, holds that lock and is alive. Only a lock judged abandoned is now removed, and a held one is named in the error.
- Fixed the OpenCode settings in `config.json` being reported by `doctor` and then ignored by the code that talks to OpenCode, which read the environment directly. A user who pointed the settings file at another port kept talking to the default one while `doctor` health-checked the port they had asked for and called it reachable.
- Fixed the daemon leaving behind a live OpenCode server it had started but that never became ready, with nothing anywhere holding its process id — so the next start adopted the broken server instead of replacing it. Ownership now follows the process handle rather than the server's reported health, and the state file distinguishes giving up from a healthy server someone else started, which it previously recorded identically.
- Fixed the OpenCode record being written only at startup, so a crash and restart moved the server to a new process id and left `clean` hunting the old one. The daemon now updates the record on every change, and declines to write once shutdown has released the file.
- Fixed `doctor` exiting successfully on a machine where the next `looptroop start` would be refused outright for want of the OpenCode binary, and on one where the running daemon's OpenCode server had died — both being exactly the question the command is run to answer. It now weighs whether a server is answering, whether a daemon is relying on one, and whether a start could launch one, and repeats the reason the supervisor recorded when it gave up.
- Fixed `looptroop setup` returning success whatever happened, so `--yes` in a provisioning script read as a clean run when the daemon had failed to start, when it would not answer for its own projects, and when the repository was rejected.
- Fixed `clean --apply` reporting success while an OpenCode server it had tried to stop was still running, and still holding the port the next start wants. A provisioning script read that as a clean machine and moved on.
- Fixed `looptroop clean` failing with a raw database error, and leaving an empty database behind, on a machine where the daemon had never started — the state in which people reach for it. It now treats a missing database, one with no tables yet, and one it cannot read as the same answer: nothing is known to be attached, which is never grounds to delete anything. It also keeps projects whose local data has gone missing, whose worktrees are precisely the debris the command exists to find.
- Fixed the daemon log growing without bound. It was rotated once, just before the daemon was spawned, which bounds it only for daemons that get restarted — and this one is built not to be. The running daemon now rotates by copying aside and truncating in place, which keeps its own append-mode handle valid; a foreground daemon writes wherever the user pointed it and is left alone.
- Fixed a failed update lookup counting as never having been attempted, so a machine that is offline or behind a proxy that swallows the request paid a fresh registry request and its full timeout on every single command. Failures are now rationed to the same daily interval as successes, and the last known version survives untouched.
- Fixed the interface fallback answering non-navigation requests with the interface document: a `fetch` for JSON failed at parse time with no indication where the response came from, and a missing script reported a content-type error rather than the not-found that actually happened.
- Fixed the development preflight sparing a running daemon on the strength of its recorded process id alone. A daemon lost to a crash or a dead battery leaves that number behind for the kernel to reassign, and because a spared process's whole subtree is spared with it, one recycled number landing on a shell could shield every stale development process on the machine — leaving the preflight to clean nothing and `npm run dev` to fail on a port it had just protected. The recorded start identity settles it, and where identity cannot be established the daemon is still spared and the reason said out loud, because sparing a stranger costs a port while killing an unverified daemon takes down a session someone is working in.
- Fixed the sign-in code appearing in the output captured from a foreground daemon, where anything printed is liable to be pasted into a bug report.
- Fixed `doctor` reporting a correctly configured project as unprotected. Its re-check stripped the trailing slash before asking git whether a path was ignored, and a directory-only rule matches nothing that way until the directory exists on disk — so the report was wrong right up until it stopped mattering.
- Fixed the version-single-sourcing gate failing on the update comparator's own test fixtures, which must name concrete versions on both sides to prove anything. The exemption is scoped to that one file, so a stale version literal anywhere else still fails.
- Fixed the single-instance lock admitting more than one daemon under real contention. Stale recovery moved the abandoned lock aside, inspected it, and put it back if it turned out to belong to a live daemon; between the move and the restore the canonical path did not exist, so a third process could take it exclusively and start a daemon, which the restore then wrote straight over. Five contenders racing one crashed run's lock produced two or three winners in seven rounds out of ten, each believing it owned the same databases and worktrees. Recovery now stages the replacement under a unique name and renames it into place, and every mutation of the lock goes through one claim.
- Fixed the claim serialising recovery expiring a claimant that was still running. A claim older than thirty seconds was taken over on age alone, so a daemon suspended mid-recovery — a laptop asleep, a starved container, a debugger stop — lost its claim to the next start; when it resumed it finished its own conversion, and two live processes each held the lock. Two further faults compounded it: a claim was judged abandoned while briefly empty between its exclusive creation and its first write, which is a window every claimant passes through, and releasing a claim deleted the path without checking it was still the claimant's, so a process whose claim had been taken over removed its successor's on the way out. A claim now carries a nonce and its owner's start identity, is never expired on age while its owner is provably the same live process, is re-verified immediately before the lock is replaced, and is released only by the attempt that created it. Age still decides for a claim from another machine or one whose owner cannot be identified at all, since honouring an unidentifiable claim forever would let one crash wedge every later start.
- Fixed the same window on the lock file itself, which is where it did the real damage. A lock is created exclusively and written a moment later, so between those two syscalls it exists and parses as naming nobody — and a lock naming nobody was converted on the spot, no questions asked. A contender arriving in that window took the lock out from under the process that had just legitimately won the exclusive create, and both ran. This is the fault that produced two winners in the five-contender race on a loaded runner, where being descheduled between two syscalls is unremarkable. The record is now staged under a unique name and renamed into place, so the canonical path goes from absent to complete with nothing observable in between; and because a lock written by an older build or by a writer killed mid-write still lands unreadable, a lock that names nobody is now left alone until it has been that way longer than writing one takes, rather than being converted immediately or honoured forever. Also fixed `stop` reporting a starting daemon as not running and deleting its lock: an unreadable lock was reported absent, and the removal it then attempted named a sentinel owner that could never match, so the file was left behind either way. It now says the lock exists but does not yet name an owner and leaves it in place, and clears it once it is old enough to be debris.
- Fixed process identity being unverifiable on Windows in hosted CI, where the lookup costs a PowerShell start and intermittently exceeded a bound shared with a `/proc` read. Because "cannot verify" must never be read as "not running", a suspended daemon looked unverifiable and an expired heartbeat was enough for a second daemon to reclaim a lock its owner still held. Windows now gets its own bound, a query that also answers for processes owned by another user, and tolerant parsing of the reported start time.
- Fixed the daemon releasing its lock and state while the OpenCode server it owned was still alive. Termination signalled the child and returned without waiting, so the next `looptroop start` could take the lock while the previous OpenCode still held its port — where the new daemon adopts it as somebody else's server and nothing ever stops it. Termination is now awaited under a budget and escalates to a forced kill before ownership is given up.
- Fixed the restart policy counting deaths rather than attempts, which inverted it: a server whose relaunch failed outright was marked degraded after one try, while one that restarted cleanly and crashed again got the full three — and the first case is the one where retrying helps. Failed launches and failed health checks now each cost one attempt of a bounded three, the daemon's state is updated after every attempt, and a shutdown cancels the loop immediately.
- Fixed `looptroop start` leaving behind the process it gave up waiting for. A readiness timeout was reported and nothing more, but that child is a real process holding the single-instance lock, and it may finish booting seconds after the CLI has said nothing started — leaving a daemon on a port nobody printed that the next start refuses to replace. The start now ends that child under a budget and clears the lock and state it left, both scoped to its pid and instance so a start that raced this one and won keeps its record. Identity is re-checked against a token taken at spawn, since a minute is long enough for a pid to be reissued, and where identity cannot be established the process is left alone and the user is told where to look.
- Fixed the host guard accepting any loopback request that arrived without an `Origin` header, which is exactly the shape a cross-port `<img>`, a no-cors `fetch` or a `window.open` produces — session cookie included. Such requests are now accepted only when the browser vouches for the origin through a header page script cannot forge and that, unlike a site, counts the port. The check applies only to callers leaning on the ambient cookie; a script holding the API token never needed the browser's word.
- Fixed the read-only installation check failing for the wrong reason and passing for the wrong one. `sudo -E` keeps the environment but still replaces `PATH` with sudoers' `secure_path`, so the installed launcher resolved the runner image's Node 22 rather than the pinned 24.15.0, exited in milliseconds, and the version mismatch was read as a read-only failure. The interpreter floor is now checked explicitly. The verifier also bound a fixed port, so a machine already running a daemon produced a pass from somebody else's process, and a survivor of a failed run was left holding the lock; it now takes a kernel-assigned port, matches the health response against the state file it wrote, reaps what it started, and prints the start output and daemon log with nonces and tokens redacted before cleaning up.
- Fixed CI resolving the toolchain rather than pinning it. `node-version: 24` selects the newest patch, so the version `engines` promises was tested on Linux alone while macOS and Windows ran whatever was current that week; and every `npm ci` used the npm bundled with the runner image — 10.9.8 on Ubuntu — rather than the 11.12.1 the repository declares, which is the resolver and lockfile reader differing from what a developer runs.
- Fixed the installed-package smoke test proving the session cookie worked by sending it the way no browser does. It presented a bare cookie with no browser context, which the new same-origin guard correctly refuses, so a test written to show the sign-in path working could only report failure. It now sends what a browser sends, and additionally asserts the case the guard exists for: the same cookie, offered as another loopback port would offer it, is turned away.
- Fixed the lock identity tests sampling process identity once and treating the answer as a property of the platform. `readProcessStartToken` returns null both where a platform cannot report start times and where the lookup simply did not answer, and on Windows it answers by starting PowerShell — which a loaded runner can push past its bound. A sample that came back null sent the test down its no-identity branch while the implementation, asking again microseconds later, got a real token: the two disagreed and the assertion failed, on the blocking Windows lane, with the advisory Windows lane passing on the same commit. Identity is now resolved once before any test branches on it and retried so a single slow lookup cannot decide it, and the value is then relied on rather than re-read — the lookup caches this process's own pid, the one pid whose token cannot change while we are the one asking, and the tests share that module with the implementation, so both sides now answer from the same cache by construction. Where a claim names another process, whose token is deliberately never cached, a failed lookup is asserted as the documented age-based fallback instead of its opposite.
- Fixed the multi-process lock test being able to fail without an exclusion failure. A winner held for a fixed quarter-second, so five processes on two cores could leave a contender descheduled past the release, and its perfectly legitimate acquisition afterwards read as a second winner. Winners now hold until every loser has reported, the assertion checks directly that no two hold intervals overlap rather than only counting winners, and a failure prints what each contender did.
- Fixed the log projection test exceeding the shared 20-second budget on Windows. Its three hundred appends are what the pagination assertions are about and cannot be reduced, and on a hosted Windows runner the per-write filesystem cost makes the same eight tests take thirty-seven seconds against one and a half here. The budget is raised for that one test rather than the whole project, and deliberately not by retrying a test that is not flaky.
- Fixed a required check being able to name a lane that cannot fail. Advisory lanes run under `continue-on-error` and report success however they went, and their job names differed from the blocking lanes' only by a version string — so one commit's required `Test (windows-latest, Node 24)` could become the next commit's advisory lane and go on reporting success forever. Advisory lanes now carry that word in the name branch protection matches on.
- Fixed the Windows test lane failing on a different innocent test almost every run. Two causes, both of them the test runner being told the machine is bigger and the work lighter than either is. The worker pool was a hardcoded six, which is comfortable on a developer machine and oversubscribes a four-core runner, so tests crossed their timeout for want of a CPU rather than for any defect of their own — three jobs on one commit produced three disjoint sets of timeouts, none in the files that commit touched. And a set of tests that drive the real database and real git worktrees had been filed into the bucket documented as pure logic, which is a shared-worker thread pool carrying the tightest budget in the suite. `createInitializedTestTicket` spends nine synchronous `git` spawns per ticket before an assertion runs; a synchronous spawn blocks the whole thread, and Windows has no `fork()` to make process creation cheap. Measured on a hosted runner, four of the five slowest files in that bucket were these, led by one spending 47.8 seconds against a 15-second per-test timeout. The pool now sizes itself to the machine and leaves a core for the process supervising it, and those tests run in the integration bucket, where each gets its own process and the budgets written for that workload. Neither is a raised timeout on a test that was never slow, and no lane retries.
- Fixed the release PR workflow being unable to commit the release it had just prepared. The bump archives the notes to a new file under `.github/releases/`, and the commit named its four paths as a pathspec — which Git resolves against paths it already knows, so a file that has never existed fails the whole commit with `did not match any file(s) known to git`. The first release PR would have stopped at that step, and so would every one after it. The four files are now staged by name first and the commit is still restricted to exactly them, so nothing a previous step left in the index rides along and nothing is ever added wholesale.
- Fixed the release's read-only installation gate being unable to pass. Bind-mounting needs a privilege the ordinary runner user does not have, and the release invoked the verifier as that user while also setting the flag that makes an unavailable mount a failure rather than a skip — so the check could only fail, and it gates the publish. CI's own invocation of the same script already had the privileged form; the release now matches it, with the interpreter resolved before elevation because the sudoers policy replaces `PATH` and would otherwise select the runner image's Node rather than the pinned one.
- Fixed the requested version being substituted into the release PR workflow's shell source at three steps rather than read from the environment. Workflow expressions are expanded before the shell sees the script, so a version string carrying shell metacharacters would run as those steps' own commands — and a later step in the same job holds the token that pushes branches and opens pull requests. Every other step already took the version through the environment; these three were the exceptions.
- Fixed the release's draft-resume path trusting a string. Resuming onto an existing draft compared only the attached manifest's integrity field and never looked at the attached tarball, so a draft carrying this build's manifest beside another build's tarball — or beside no tarball at all — was accepted and published. It now requires both assets to be present, downloads them, compares every manifest field including the commit, and hashes the downloaded tarball against it; a mismatch stops the release instead of publishing bytes nobody verified.
- Fixed `--out` and `--registry-integrity` being unusable in the release manifest and artefact-verification scripts. Both discarded arguments beginning with `--` and counted what remained as positionals, but a flag's value is not a flag: the path or the integrity string was counted as one positional too many, so every invocation using the flag the script documents was rejected with the usage message. Values are now excluded by position. The manifest tool also shortened its closing output path by slicing the repository root's length off the front whether or not the path was inside the repository, so writing to a staging directory elsewhere reported having written a file in the checkout; it now shortens only what genuinely is inside.
